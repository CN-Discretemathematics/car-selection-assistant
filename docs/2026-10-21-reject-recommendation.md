# 「不喜欢这台」→ 拒绝后不再推（2026-10-21）

> 分支：`feat/reject-recommendation`｜基线：`origin/main`（不依赖任何未合入分支）

## 场景出处

《2026-10-20 架构收敛与产品方向清单》§3.3 定的多轮评测场景之一是
**「拒绝后不再推」**：用户看���推荐后否掉某一款，后续不该再推它。

本笔做的是这件事的**会话内**一半：用户说「不喜欢这台」→ 这一款进排除集 →
后续推荐不再出现。

跨会话的那一半（拒绝要**记住**，并按拒绝理由调偏好）需要**反馈表**，
而反馈表的迁移必须接在分支 8 的迁移之后（否则 alembic 会出现两个 head），
因此留在 Phase 2 的下一笔。

## 语义边界（三条，都写明以便推翻）

1. **只认带指示词的否定**：「不喜欢这台」「不要这辆」「别推它」。
   裸的「不要」（「不要 SUV」「不要电车」）是**硬约束**，走 `avoid` / 品牌排除
   那条路——两者混在一起会把一整类车误伤成一款车。
2. **指的是「刚推荐的那一款」**（`last_recommended_variant_ids` 的最后一个）。
   一轮给了多张时确有歧义，所以回执里说清是「刚推荐的那款」——
   用户说车名可以再纠正（诚实性：不假装确定）。
3. **只在会话内生效**。跨会话要靠反馈表 + 影子调参。

## 实现要点

- **画像新增 `rejected_variant_ids`**：与 `avoid` 分开——`avoid` 是
  **车型/能源维度**的排除（「不要 SUV」），这里是**具体某一款**被否掉，粒度不同。
- **过滤两处口径一致**（本仓惯例：SQL 下推 + Python 兜底）：
  - SQL：`~VehicleVariant.id.in_(profile.rejected_variant_ids)`；
  - Python：`variant.id in profile.rejected_variant_ids` → continue。
  两处少一处都是半修：只留兜底意味着全库扫描时仍把被拒的车捞进候选集。
- **不额外加一次落盘**：画像下方那次「吸收变更」的**无条件写**会把它一起持久化。
  `tests/test_profile_persistence.py` 钉死了「`respond()` 里无条件落盘恰好两处」，
  中间插一次写会破坏那个结构契约。
- **要 `structured = True`**：这句话本身不含任何硬约束，但它是**明确的信号**；
  不置位就会被当成闲聊 → 掉进 LLM 对话分支 → 用户看到一句无关的回话，
  推荐根本没重出。

## 证据

- 后端 **1305** 用例全过（origin/main 基线 1299 + 本分支 6）。
- **变异测试 4/4**：M1 认不出拒绝表述 / M2 SQL 侧不下推（只留 Python 兜底 = 半修）/
  M3 Python 侧兜底被删 / M4 拒绝不算结构化输入（掉进闲聊分支，推荐不重出）——
  全部被抓住（脚本 `.tools/mutate_rj.py`，本地专属不入库）。
- 六条用例都带**前提断言**（被拒的那款本来就在候选里；没有记忆/推荐时如实说），
  否则测的是空气。
- 其中一条是**源码级契约**（SQL 下推 + Python 兜底两处都要在）——
  端到端看不出「只留兜底、去掉下推」这种半修。
