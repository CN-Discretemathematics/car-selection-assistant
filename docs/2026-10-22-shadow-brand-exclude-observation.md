# 影子档看不见品牌排除项：观察期的判据是残的（2026-10-22）

> 来源：2026-10-22 生产影子日志复查（cron 复查任务）+ 生产 13 条代表性探针实测。
> 分支：`fix/shadow-brand-exclude-observation`

## 一句话

`shadow` 档的观察日志**结构性地没有** `brand_exclude`——7 个被跟踪键里少了 1 个
⇒ 「观察够了就切 `on`」这道判据**看不见该看的**，切过去才发现品牌排除没被记住。

## 怎么发现的（生产实测，不是推演）

生产 `shadow` 档对 13 条代表性探针跑一轮，取容器日志里的
「偏好记忆（shadow，未写库）」共 13 条（另 1 条是部署前的人工验证，不计入分布）：

| 键 | 命中 | 探针（节选） | 抽到的值对不对 |
| --- | --- | --- | --- |
| `usage` | 6/13 | 家用 / 通勤 / 家庭 / 商务 | ✓ |
| `body_type` | 6/13 | SUV / 轿车 / MPV | ✓ |
| `energy_preference` | 3/13 | 纯电 / 插混 | ✓ |
| `budget` | 8/13 | 15 万 / 20–30 万区间 / 25 万 | ✓ |
| `passengers` | 3/13 | 5 口 / 5 人以上 / 7 座 | ✓（「5 人以上」按开区间取 6 座，是产品拍板的口径） |
| `avoid` | 2/13 | 不要燃油车 / 不喜欢轿车 | ✓（否定作用域正确：只排除轿车，不牵连同一句里的 SUV） |
| **`brand_exclude`** | **0/3** | 不考虑比亚迪 / 不要特斯拉 / 别要大众，也别要长安 | ✗ **结构性缺失** |

⇒ 其余六键**值全对**；唯独「品牌排除」三条探针**一条都没记上**。

## 根因

`app/agent/preferences.py`：

```
effective_brand_exclusions():        if not mode_capabilities().refill:  return {}
persist_hints()（shadow 分支）：      if brand_exclusions: effective["brand_exclude"] = labels
```

`refill` = 「回填进画像」——它会**改变推荐结果**，所以 `shadow` 档为假。
整个 `effective_brand_exclusions` 被这道门短路 ⇒ `shadow` 档（`observe=True` /
`refill=False`）**恒返回 `{}`** ⇒ `persist_hints` 里那段**专门为 `brand_exclude`
写的赋值在 `shadow` 下是死代码**。

这不是「设计如此」：`persist_hints` 明确为它准备了赋值分支，说明**意图就是要
在影子日志里看见它**；只是它拿到的输入恒为空。

「算出排除项」≠「回填进画像」：**算出来给日志看，不需要回填**。

## 影响

1. 观察期**看不见** 7 个被跟踪键里的 1 个 ⇒ 「影子日志攒够了就切 `on`」
   这道判据是**残的**：攒够了也可能漏了这一路。
2. 影子日志里出现「这一轮没有可记的东西」（`{}`），会被误读成
   「用户什么都没说」——实际是**解析出来了但被闸门丢了**。

## 改了什么

`effective_brand_exclusions` 的门从 `refill` 换成 `observe`
（`observe` = 解析身份 + 落观察日志，`off` 档为假）。

**零行为变更**：回填那道门仍在 `restore_into_profile` 自己身上（`refill`），
⇒ `shadow` 档画像依然**不被回填** ⇒ 推荐结果逐位不变，只是影子日志多出
`brand_exclude` 这一个键。`on` 档（`observe` 与 `refill` 同为真）行为不变；
`off` 档（两者同假）行为不变。

## 验证

新增 `backend/tests/test_agent_shadow_brand_exclude.py`（8 条）：

| 断言 | 抓什么 |
| --- | --- |
| `shadow` 算得出本轮排除项 | 闸门短路 |
| `shadow` 影子日志看得见 `brand_exclude`（值是**名**不是 id） | 观察缺口本体 |
| `persist_hints` 的 `brand_exclude` 分支**不得是死代码** | 这一类缺陷（生产实测里它安静地不可达了一个影子周期） |
| `shadow` **仍不写库** | 「看得见 ≠ 写进库」 |
| `shadow` **仍不回填画像** | 零行为变更的保证 |
| `on` 照旧写入品牌排除项 | 回归护栏 |
| `off` 照旧什么都不算 | 回归护栏 |
| 端到端（HTTP 链路）影子日志看得见排除项 | 同构复现生产现象 |

**变异测试**：把闸门改回 `not mode_capabilities().refill:` ⇒ **4 条变红**
（算得出 / 日志看得见 / 不回填的前提 / 端到端），其余 4 条仍绿
⇒ 新断言不是摆设。

## 切 `on` 的建议（待人拍板，本笔**不**动闸门）

**建议：先不切**，等本笔上线后重新攒一轮影子日志——理由不是「样本不够」，
而是**上一轮的样本本身就是残的**（少了品牌排除这一路）。

切 `on` 的两条前提见 [deployment.md §9](deployment.md)；
本笔补上的是前提 1 的**完整性**：修好后影子日志才会覆盖全部 7 个键。

另有一条与闸门无关的事实：生产**目前没有任何自然流量**
（`agent_turn_logs` 24 条全是人工验证，容器日志里除健康检查外只有这些探针），
⇒ 靠「等用户来」攒样本，在有真实用户之前是攒不出来的。
攒样本要么靠真实用户，要么靠这样一组可复现的代表性探针。

## 附：复现用的探针集

覆盖 7 个键 + 两个易错点（否定作用域、歧义品牌排除）：

```
预算15万，家用5口人，想要家用SUV            # 预算 + 用途 + 人数 + 车身
预算20到30万之间，想要纯电轿车通勤用        # 区间预算 + 能源 + 通勤
25万左右的SUV就好                          # 「左右」预算
5人以上坐的MPV，家庭出行                    # 开区间人数
不要燃油车，我想要插电混动的                 # avoid + 能源（否定不得牵连）
不喜欢轿车，SUV可以                        # 否定作用域：只排除轿车
不考虑比亚迪，预算20万以内                  # 品牌排除（非歧义）
不要特斯拉                                # 品牌排除（独立一句）
别要大众，也别要长安，预算15万               # 品牌排除（歧义品牌 ×2）
自己开通勤用，10万以内的小车                # 「自己用」⇒ 通勤
商务用途，30万以内，7座                    # 用途 + 人数
插电混动SUV，家用，预算20万                 # 组合
你好                                      # 闲聊：影子日志应为 {}
```
