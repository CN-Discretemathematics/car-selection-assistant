# D1.1 款型名上下文消歧（2026-10-21）

> 分支：`feat/variant-name-context-disambiguation`｜基线：`origin/main`（不依赖任何未合入分支）

计划 §四「第二步：Phase 0（三个确定性缺口）」的第一项：**D1.1 款型名上下文消歧**。
（计划 §四 明说：品牌点名判定单一入口是它的**前置**——「在消歧口径还没统一的代码上
做上下文消歧，等于在会漂的地基上盖第二层」；该前置已在 `refactor/brand-mentions-single-entry` 落地。）

## 问题

库里的**款型显示名不含车系名**：「2026款 标准版」「2026款 Ultra」「2026款 Hi4-T」。
生产库实测 **103 个**归一化款型名被**多个车系共享**：

| 撞名款型名 | 共享的车系 |
| --- | --- |
| `2026款ultra` | 理想L6、理想L8、理想L9、岚图泰山、智界V9 |
| `2026款pro` | 迈腾 PHEV、探岳L PHEV、乐道L80、创维EV6 |
| `2025款豪华版` | 标致5008、星际X新能源、Polestar 4 |

撞名名此前**整体不入名称索引**（first-wins 会造出幽灵第二实体，把单车系问答误判成对比），
于是用户点名了款型也只能按**全系**给值：

```
前：风行T5 EVO 2024款 1.5TD DCT尊享版 的电机功率是多少
    你问到的相关参数：最大功率 = 145 kW；最大功率转速 = 5600 rpm / 5200 rpm（不同款型存在差异）；
                       最大净功率 = 130 kW / 140 kW（不同款型存在差异）；…
后：你问到的相关参数（按「风行T5 EVO 2024款 1.5TD DCT尊享版」）：最大功率 = 145 kW；最大功率转速 = 5600 rpm；
                       最大净功率 = 130 kW；…
```

答非所问——用户问的是**那一款**，回答给的是**全系的多档值**。

## 机制

- **款型名索引**（`catalog/series_index.py::_load_variant_entries`）：
  归一化款型名 → `[(variant_id, series_id)]`，**保留撞名**（车系名索引不敢收它们）。
- **`resolve_variants(db, message, context_series)`**：解析用户点名的具体款型。
  消歧规则（宁可漏判不可错判）：
  1. 款型名**唯一** → 直接命中；
  2. 款型名**撞名** → 消息里**就近**的车系名若在候选集内就归它；
     并列最近（信息不足）→ **不猜**；没有上下文 → **不猜**。
- **车系问答**（`agent/series_qa.py::build_series_qa_answer`）：
  解析出**唯一一个**款型时，参数改用**该款型**的事实，并在文案里点名是哪个款型。

## 实测（引擎级 A/B，本地快照库 908 车系 + 真实题库 520 题）

同一批输入，改动前后**用户可见回答逐字比对**（确定性链路，语料 `eval/questions.json`）：

| 指标 | 数值 |
| --- | --- |
| 回答发生变化 | **39 / 520**（7.5%） |
| 异常 | 0 |
| 按意图 | `param_variant_key` 35 · `compare_two` 4 |

其中 **38 条**的新回答带「（按「X 款」）」限定语——即**参数从「全系多档值」变成了
「用户问的那一款的值」**。

题库侧的分布（改动前后同源统计）：520 题里 **121 题**点名了款型，其中 **46 题**的
款型值与全系值不同（36 走车系问答路径、13 走版本差异路径、7 走对比路径——后两类
本来就精确到款型，不在本次改动范围）。

## 三个被实测揪出来的坑（都不是「产品缺陷」，是**实现缺陷**）

1. **同一份缓存、两个写者** → 款型索引永远为空。
   车系名索引与款型名索引共用一份指纹缓存，但**只有车系那条路径会写缓存**。
   于是「先解析车系、后解析款型」时，款型索引拿到的永远是首次刷新留下的空字典
   → 款型**一个都解析不出来**。
   **症状极具欺骗性**：引擎级 A/B 跑完「0 题变化」，看起来像「这个特性没用」，
   实际是「特性根本没生效」。修法：两份索引**原子刷新**（`_ensure_index`）。
2. **「同系多款型」误收窄** → 把差异的来源藏了。
   「A 的 X 款 和 Y 款 差在哪」收窄到其中一个款型后，**另一个款型的值消失了**——
   而那几个值正是差异的来源（实测 15 题 `variant_diff` 受影响）。
   修法：同一车系点名了**多个**款型时不收窄。
3. **夹具里「第一个候选」恰好是正确答案** → 守卫测不出「靠上下文」。
   变异 M1（撞名不看上下文）报 MISS：忽略上下文时选中的候选**正好**是期望答案。
   修法：夹具改成「**错误候选排在前面**」（乙车系先种）+ 索引查询加确定性
   `ORDER BY series_id, id`（撞名候选顺序必须可复现）。

## 行为变更

| 场景 | 变更 |
| --- | --- |
| 用户点名**唯一**款型名 | 参数从「全系多档值」改为该款型的值，并加限定语「（按「X 款」）」 |
| 用户点名**撞名**款型名、同句有车系名 | 按上下文消歧后同上；消歧不确定则**维持原样** |
| 同一车系点名**多个**款型 | **不变**（要看的是款型之间的差异） |
| 该款型在库里没有事实 | **不变**（不退化成「官方资料未披露」——那是假否定） |
| 没点名款型 | **逐字不变** |

打分与排序未变（本分支不碰候选集与评分）。

## 已知边界

- **只做消息局部上下文**（同句共现的车系名）。会话里**锁定**的车系属于跨轮上下文，
  本函数不碰——「那 2026款 Ultra 呢」这类追问仍退回全系口径。
- 只改**按需参数**（`probe_facts`）那一段；「核心参数（全系极值）」那一行**保持全系口径**
  （它的标签就写着「全系极值」，收窄它会与文案自相矛盾）。
- 对比路径（`comparison_tool`）与版本差异路径本来就精确到款型，不在本次改动范围。
- 撞名款型名的候选集来自**当前库**；库更新后候选会变（索引按指纹自动重建 ✓）。
