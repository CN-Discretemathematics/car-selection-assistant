# 检索架构决策：保留「进程内 BM25 + 向量」两路自研融合，不上 Milvus 原生 hybrid（2026-10-23）

> 触发：用户问「为什么向量库后台只有 search、没有混合检索」⇒ 顺带评估了「换原生 hybrid_search」的收益。
> 结论（用户拍板）：**保留现状**。
> 分支：`chore/deploy-warmup-sparse-index`（本笔一并落地「部署后预热」）

## 现状：混合检索发生在**我们这边**，不在向量库里

| 环节 | 在哪 | 向量库能看到吗 |
| --- | --- | --- |
| 稀疏召回（BM25，中文 bigram 分词） | **进程内**（`InMemoryRetriever`） | ❌ |
| 稠密召回（embedding） | Zilliz `POST /v2/vectordb/entities/search` | ✅ 记成 `search` |
| **RRF 融合**（k=60） | 进程内（`app/rag/pipeline.py::_fuse`） | ❌ |
| cross-encoder 重排 + 把关 | 进程内 | ❌ |

⇒ 向量库只承担其中一路 ⇒ 后台只有 `search` 是**架构的正确反映**，不是漏了什么。

## 原生 hybrid 的收益，逐条对照

| 收益 | 对我们 |
| --- | --- |
| 稀疏索引常驻服务端 ⇒ 不用每次重建 | ✅ **最实在的一条**（见下面的实测代价） |
| 索引持久化 + 可横向扩展 | ⚠️ 现在多 worker 会**各建一份** BM25（内存 ×N、每 worker 各付一次重建；**检索结果本身一致**，不是「分裂脑」） |
| Zilliz 后台指标一体 | ✅ 监控/计费口径统一 |
| 一次 RTT 拿两路召回 | ❌ **我们已经并行**（`recall_sparse ∥ recall_dense`）⇒ 零收益 |
| 服务端加权（WeightedRanker） | ❌ 我们能**按查询类型动态切权重**（默认 sparse 0.6 / dense 0.4，语义查询由查询路由在运行期切）⇒ 服务端静态权重是**倒退** |
| 降级兜底 | ❌ 现在向量库挂了还有 BM25 兜底；全搬进 Milvus 就变成「要么都在，要么都没有」⇒ **更脆** |
| 中文分词 | ⚠️ 我们的 bigram 是 A/B 实测选出来的（`RETRIEVAL_TOKENIZER=bigram`）；Milvus 内置 BM25 的中文分词质量**未知**，需实测对照 |

> 该实例（`*.serverless.ali-cn-hangzhou.cloud.zilliz.com.cn`）**支持**
> `hybrid_search` 与 `query` 路由（探测返回 1802「缺参数」而非 404）⇒
> **不是实例不支持，是我们没调**。

## 我们这套的真实代价（2026-10-23 实测，生产）

| 场景 | 耗时 |
| --- | --- |
| 进程内 BM25 重建（14032 chunk） | **5.37 秒** |
| **新进程的首个检索**（≈ 容器重启后的第一个用户请求） | **6.42 秒** |
| 同一进程之后的检索 | **0.69 秒** |

⇒ **每次部署后，第一个用户请求要多付 ~5.7 秒**（端到端从 ~4s 变成 ~10s）。
原因：容器一重建，进程内 BM25 就空了 ⇒ 由**那个请求自己**同步重建
（`service.py::_invoke` 里调 `ensure_sparse_index`）⇒ 而部署脚本的健康检查打的是
`/api/v1/ready`（不触发检索）⇒ **没人预热**。

## 决策：不换架构，改用「部署后预热」

**要换原生 hybrid 才能解决的问题，其实只有一个**：部署后首请求慢 5.7 秒。
而这个问题**不必换架构就能消掉** ⇒ `deploy/carsel-deploy.sh` 在切流后主动打一次
检索（`warmup_retrieval`），把这笔钱花在部署窗口里。

- 端点：管理后台的 RAG「试运行」（`/api/v1/admin/rag/query`）——
  **只跑检索链**（分词 → BM25 → 向量 → RRF → 重排），**不调 LLM、不调 embedding**
  ⇒ 预热成本 ≈ 5.4 秒 CPU，零外部调用费用；
- 必须打在**运行中的新进程**上（另起进程建的索引会随那个进程退出而丢弃）；
- **预热失败 ⇒ 回滚**（检索链都不通，这次部署不算成功）；
- 找不到 admin token ⇒ **跳过预热但不阻断部署**（降级不制造新的失败面）。

⇒ 用户的第一笔请求从此是 **0.69 秒**，而不是 ~10 秒。

## 什么时候**才**该重新评估原生 hybrid（两个信号）

1. 要开**多 worker / 多实例**（现在 BM25 内存与预热成本 ×N）；
2. 想让**向量库后台成为唯一检索观测面**（现在两套指标：Zilliz 的 `search` +
   我们的 `/admin/rag/runs` 瀑布图）。

⇒ 那时的评估材料：迁移方案 + 影响面 + `backend/tools/eval_rag.py` 前后对照
（当前 Hit@K/MRR 与 0.6/0.4 权重都是针对「自研 BM25 + 向量」这一对**调出来的**，
换组合必须重跑评测重调权重）。

## 另一条容易踩的坑（已实测）

**别只看向量库后台判断检索量**：一次用户检索 = 1 次 Zilliz `search`
+ 1 次进程内 BM25 扫描，后者**完全不出现在 Zilliz 的监控与账单里**。
⇒ 真实的检索轨迹要看**我们自己的** `/admin/rag/runs`（每一步的 sparse/dense 命中数、
RRF 权重、reranker、耗时）。
