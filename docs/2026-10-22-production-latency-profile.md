# 生产首轮延迟的分段实测（2026-10-22）

> 来源：2026-10-22 生产实测（`shadow` 档，5 轮**完整推荐轮**）。
> 分支：`chore/production-latency-profile`（纯文档分支）

## 一句话

端到端 **2.7–6.7s（中位 ~4.0s）**；**瓶颈是 LLM 解释生成（占 53%–67%）**，
**不是检索**（三件套合计只占 8%–11%）。
先前记的「首轮 10.5s」是**长尾样本**，不是常态——别再拿它当基线。

## 怎么测的

- 对生产发 5 条**信息齐全**的消息（预算 + 用途 + 人数 + 车身都有），
  确保走**完整推荐链**而不是「最小化追问」分支（追问分支只要 36–49ms，测不出东西）。
- 端到端用 HTTP 往返计时；分段用**容器日志的时间戳还原**：
  httpx 的日志在**响应收到时**打印 ⇒ 相邻两条 httpx 日志的间隔 = 上一段的耗时；
  `app.agent.respond` 的 `elapsed_ms` = 引擎内整轮耗时。

## 数据

| 轮 | 输入 | 端到端 | embedding 往返 | Zilliz 检索 | rerank | **LLM 生成** | 本地（画像+SQL+序列化） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 15万 / 家用5口 / SUV | 4381ms | 875ms | 99ms | 206ms | **3021ms** | ~180ms |
| 2 | 20万 / 5口通勤 / SUV | 6634ms | 1588ms | 130ms | 328ms | **4430ms** | ~158ms |
| 3 | 30万 / 7座MPV / 家庭 | 3780ms | 433ms | 109ms | 303ms | **2790ms** | ~145ms |
| 4 | 25万 / 5人 / 纯电SUV | 3958ms | 607ms | 102ms | 216ms | **2320ms** | ~713ms（跑了**两轮**检索） |
| 5 | 20万 / 家用5口 / 插混SUV | 2741ms | 722ms | 129ms | 283ms | **1446ms** | ~161ms |

（HTTP 端到端比 `respond` 多 ~50ms：请求解析 + 响应序列化。）

**读法**：

1. **LLM 解释生成是大头**：1.4–4.4s，占端到端 **53%–67%**。
2. **检索不是瓶颈**：embedding + 向量库 + rerank 三件套合计 0.3–0.5s（8%–11%）。
3. **本地开销可忽略**：画像解析 + SQL 候选扫描 + 序列化 = **~150–180ms**
   （候选扫描量 870–3887 也没差别 ⇒ 不是 DB 的问题）。
4. **embedding 往返波动大**：0.43–1.59s，另有一轮实测到 **6.3s**（早先那次 10.5s 的样本就在这一段）。
5. 第 4 轮跑了**两轮**检索链（多花 ~530ms）——触发条件未查明，值得盯。

## 结论与建议（按性价比排序）

**别优化检索**（只占 10%），要动就动生成侧：

1. **先出卡片、后补解释**：推荐卡片的数据全是本地算的（~180ms 内），
   而解释文本要等 LLM 1.4–4.4s ⇒ 把两者解耦能让「首屏可见」从 ~4s 降到 ~0.2s。
   schema 里 `recommended_variants` 与 `explanation` 本来就是分开的字段，
   前端 `AgentChat.tsx` 目前是等整包返回才渲染。
2. **确认前端是否用 SSE**：后端已有 `/agent/sessions/{session_id}/stream`（SSE 重放），
   但主链路仍是同步返回。若改成流式，首字延迟可再降一截。
3. **embedding 缓存**：同一句话的 query embedding 可复用（省 0.4–1.6s，
   长尾省 6s）；也可以给 embedding 调用加超时降级（拿不到就走纯 SQL 排序）。

## 与「10.5s」那条旧记录的对照

早先记的「首轮 10.5s」= 一次长尾：embedding 往返 6.3s + LLM 生成 2.1s。
本轮 5 次的中位是 4.0s、最慢 6.7s ⇒ **10.5s 是 p95+ 的样本，不是 p50**。
引用这个数字时应写「长尾 10.5s / 常态 2.7–6.7s」。

## 附：复现方式

生产容器里 `docker logs deploy-api-1` 就有全部时间戳；
`httpx HTTP Request:` 行按时间顺序读，相邻两行的时间差就是上一段耗时。
注意：**路由 LLM 是旁路任务**（`app.agent.router.shadow` 在整轮结束后才落日志），
它的 `deepseek` 那一行会落到**下一轮**的窗口里——分段时别把它算进本轮。
