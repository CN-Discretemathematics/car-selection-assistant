# 拒绝跨会话记住（Phase 2b「反馈表」）

> 分支：`feat/durable-variant-feedback`｜日期：2026-10-21
> 依赖：分支 8（跨会话偏好记忆 + `anonymous_identities` 表）已进主干

## 一、为什么要有它

「拒绝」是**最强的负反馈**：用户说「这台不要」就是不要。

但会话内拒绝（`profile.rejected_variant_ids`）只在**本次对话**有效 ⇒
下次会话又会把用户明确说过「不要」的车推给他 ⇒ 用户会觉得「**它没听我说话**」。

⇒ 需要一张**反馈表**：把「用户拒绝过哪一款」记下来，跨会话读回。

## 二、表与读写路径

### 表 `variant_feedbacks`

| 列 | 含义 |
|---|---|
| `identity_id` | 归属的匿名身份（跨会话的载体 ✓） |
| `variant_id` | 被拒绝的款型 |
| `series_id` | 该款型所属车系（冗余，便于按车系聚合与审计 ✓） |
| `reason` | 用户给的理由（原话，可空 ✓）——**只留痕，不参与任何推荐判定** ✓ |
| `(identity_id, variant_id)` | **唯一** ⇒ 同一款型重复拒绝只留一行（幂等 ✓） |

### 写

拒绝发生时（`engine.respond` 的拒绝分支）⇒ 取「拒绝前后排除项的**差集**」
⇒ 写进反馈表 ✓（已排除过的款型不重复写 ✓）。
车系级拒绝（「甲车系不要」）在**写入时**就展开成该车系**全部在售款型**的行 ✓。

### 读

会话开始时（`turn.advance_profile`）⇒ 读回这个身份拒绝过的款型 id
⇒ **并进 `profile.rejected_variant_ids`** ✓。

⇒ 推荐链因此**完全复用**会话内拒绝那套排除逻辑（工具层**零改动** ✓）
⇒ 两种排除的行为**必然一致** ✓（仓库纪律：同一件事不许写两遍 ✓）。

## 三、三模式闸门

沿用偏好记忆那一套 `DURABLE_PREFS_MODE` ✓：

| 模式 | 写 | 读 | 效果 |
|---|---|---|---|
| `off` | ✗ | ✗ | 行为与接入前**逐位相同** ✓ |
| `shadow` | 只落日志 | ✗ | 可观测，不改行为 ✓ |
| `on` | ✓ | ✓ | 拒绝跨会话记住 ✓ |

⚠️ **会话内**的拒绝**不受模式影响**（它本来就是硬约束 ✓）——
模式只管**跨会话**那一半 ✓。

## 四、A/B 实测

| 场景 | 结果 |
|---|---|
| 会话 1 说「甲车系不要」→ **新会话**再问同一需求 | 甲车系**不再出现** ✓（另两个车系照常推 ✓） |
| 同上，但 `DURABLE_PREFS_MODE=off` | 甲车系**照旧出现** ✓（= 接入前的行为 ✓） |

第二条是**反证**：只测「记住时生效」的话，一个「什么都没做但恰好没推」的实现也能通过 ✓。

用例：`backend/tests/test_variant_feedback.py`（5 个：存储往返 / `off` 不写 /
重复拒绝只留一行 / 端到端跨会话生效 / `off` 端到端不记住 ✓）。

## 五、纪律

- **写失败绝不影响**用户这一轮的正常回答 ✓（记 warning、继续 ✓，与
  `preferences.persist_hints` 同一范式 ✓）。
- **自己提交**：`get_session` 不提交 ⇒ 只 flush 不 commit 等于没写 ✓。
- 款型**不在库里**时不写（库重导入后 id 会变 ⇒ 避免悬空引用 ✓）。

## 六、还没做的（下一步）

- **反馈的影子评估**：现在只留痕，不参与任何偏好调整。计划里的
  「反馈驱动偏好调整（shadow）」目前覆盖的是**品牌级**排除（分支 17 的误伤面实测 ✓），
  款型级还没做。
- **账户合并与隐私**（Phase 3/4）：把匿名身份的反馈与记忆**合并进注册账户**，
  以及用户侧的导出/删除。依赖 `anonymous_identities.merged_user_id`（分支 8 已留该列 ✓）。
- **题库用真实拒绝原因**：反馈表攒够真实理由后，多轮题库的「拒绝原因」维度
  就不用再靠模板生成（计划 §3.3 提过这个动机 ✓）——需要一些真实数据积累 ✓。
