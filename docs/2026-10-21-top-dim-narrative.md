# 首要维度 `top_dim` 驱动叙事（2026-10-21）

> 分支：`feat/top-dim-narrative`｜基线：`origin/main`（不依赖任何未合入分支）

## 计划原文（§1.2 拍板）

| 决策 | 结论 |
| --- | --- |
| 推荐主体 | 「直击痛点」而非数据罗列：先讲用户最在意的维度，再讲代价 |
| 首要维度 | 给画像加 `top_dim`，**只影响文案组织，不动打分与排序** |

§七 把它列为**未验证判断**：「首要维度驱动叙事能提升体验」——**未做 A/B**。
本笔把机制落地**并**补上那次 A/B（见下）。

## 机制

- **画像新增 `top_dim`**（`UserProfile`）：用户**明确抬高**的那个维度
  （「我最看重动力」→ `power`）。
  ⚠️ 判据**不是**「默认权重最高的维度」——默认里 `budget` 最高（0.30），
  那是**评分口径**，不是用户的偏好。
- **`merge_profile` 负责写它**（全仓唯一的合并器，不新建第二个 ✓）：
  只在「这一轮有被抬高的维度」时更新；后说的偏好压过先说的 ✓；
  **只写这一个字段，不碰权重**（碰了就是在动打分）。
- **文案组织**（两处）：
  - 确定性模板（LLM 不可用时的回退）：**在句首点名**该维度
    （「按你最看重的动力排的」），再讲「注意妥协项」；
    **没有 `top_dim` 时一个字都不改** ✓；
  - LLM 解释模块的提示（**生产主路径**）：点名该维度并要求**先讲它**。
    提示词此前内联在 `_explain` 里，**没法单测**——本次抽成纯函数
    `_explain_system_prompt`，提示内容被用例直接钉住。

## ⚠️ 刻意**不做**的事：不把首要维度塞进「匹配项」

初版实现把首要维度提到「匹配项」最前（如「匹配项：动力、预算匹配」）。
**自查时否掉了**：

- 「匹配项」是这台车**已验证达标**的项（预算/用途/能源/座位），
  而首要维度只是**用户在意**的方向——库里可能压根没有这个维度的数据
  （`dims` 0.5 中性 = 无此数据，不是「弱」，更不是「匹配」）；
- 硬塞进去＝替这台车认领一个没核实过的达标项＝**编造**（设计原则第 1 条）。

⇒ 改为**只在句首点名**（「按你最看重的动力排的」）——这句说的是**排序口径**
（该维度确实被抬了权重、确实参与了打分），是**可证的真话**。
代价：匹配项列表里不出现该维度（除非它本来就在里面）。
边界由用例 `test_match_items_never_claim_an_unverified_dimension` 钉住。

## 三条约束各自的守卫

| 约束 | 守卫 |
| --- | --- |
| **不动打分与排序** | 只差 `top_dim` 一个字段时，分数与顺序**逐位相同**（`test_top_dim_does_not_change_the_ranking`）；写 `top_dim` 不碰权重（`test_writing_top_dim_does_not_touch_the_weights`） |
| **先讲最在意的维度** | 确定性模板里该维度被点名且**排在「妥协项」之前**（`test_explanation_names_the_top_dimension_first`）；LLM 提示里点名并要求先讲（`test_llm_prompt_leads_with_the_top_dimension`） |
| **不认领未核实的达标项** | 匹配项里不得出现没有库内证据的维度（`test_match_items_never_claim_an_unverified_dimension`） |

## 变异测试

`.tools/mutate_td.py`（本地专属，不入库）**5/5**：每个变异都被用例盖住——
① 首要维度取成「默认权重最高的维度」② 写 `top_dim` 时顺手改权重
③ 模板不点名 ④ 首要维度硬塞进匹配项 ⑤ 删掉提示里「先讲」那句。

其中 ④ 是把初版那处**否掉的实现**重新放回去——守卫确实会红。

## A/B（计划 §七 缺的那次）

同一份画像、同一批候选，**只差**解释模块提示里有没有「先讲用户最在意的维度」这一句。
判定用**二元可判**（judge 只答「是/否」）：这段回答有没有**先**讲用户最在意的那个维度。

本机真跑（本地快照库 908 车系 + 真实 LLM，12 题覆盖 4 个优先维度 × 3 组预算/用途）：

| 臂 | 先讲首要维度 | 说明 |
| --- | --- | --- |
| A（现状） | **4/12** | 两轮跑都是 4/12（很稳） |
| B（新增） | **11/12** 与 **12/12** | 两轮跑（LLM 采样有方差） |

⇒ **同一批输入，B 臂把「先讲用户最在意的维度」从 4/12 提到 11~12/12**，
即现状下**七成以上的回答根本没提用户说的那个优先级**（它们按 8 维评分顺序罗列）。

### 与最终实现的一致性

A/B 的 B 臂提示文本与最终实现的 `_explain_system_prompt` **逐字一致**
（`BASE_SYSTEM` + `PRIORITY_SUFFIX` 两段拼接），所以上面的结论对最终实现仍然成立。
A/B 测的是 **LLM 提示路径**（生产主路径）；确定性模板是 LLM 不可用时的回退。

### 事实性：这一项**没测成**，不拿它当判据

原本还想用「答案里的数字必须在候选允许集内」做确定性事实校验，但这个尺子**两版都不准**：

- 第一版把「元」和「万」当两个数 → 两臂各 12/12 全被误报成「编造」；
- 第二版补了单位变体、年款、来源 id、推导差值后，仍把**合法**的评分
  （`0.978`）、预算（`20`）、来源 id（`3`）当成越界；
- 相对检查（B 臂的数字 ⊆ A 臂）也不成立——**两臂是独立采样**，数字本来就不同。

⇒ 数字自检**作废**（不作为判据，也不写进结论）。
事实性的**权威守卫仍是仓库既有的回答契约**（`answer_contract.py`：每次发送前
逐个数字自证，找不到依据就回灌重写，仍不合格就回退确定性文案）——它对两臂**同样**
生效，由全量用例守住。

### 结论的边界

测到的是**可观测代理**：「回答有没有先讲用户最在意的维度」。
「这样是否**更招人喜欢**」仍是**产品直觉**——没有用户测试 ✗（计划 §七 的告诫依然成立），
本次只把「机制是否真的起作用」从**未验证**变成**已验证** ✓。

## 行为变更

| 场景 | 变更 |
| --- | --- |
| 用户**明确抬高**某个 8 维关键词（如「我最看重动力」） | 解释模块提示点名该维度并要求先讲它；确定性回退文案句首加「按你最看重的动力排的，」 |
| 其他所有场景 | **一个字都不改**（无 `top_dim` → 提示与文案逐位不变） |
| 会话画像存储 | `UserProfile.model_dump()` 多一个 `top_dim` 键（缺省 `null`，旧画像不受影响） |

打分与排序**未变**（有用例钉住：分数与顺序逐位相同）。

## 已知边界

- 只认**明确抬高**的表达（「我最看重动力」「主要看空间」）。「后排大一点」这类
  没有落到 8 维关键词表的说法**不产生**首要维度（本仓既有约束：没有关键词入口的
  维度不算，因为「加权却测不到 = 白白稀释其它维度」）。
- 「安全」**刻意不映射**任何维度（计划 §1.2 与仓库既有立场：安全没有可计算的
  维度，映射过去等于**用行为冒充理解**）。所以「我最看重安全」不产生 `top_dim` ✓。
- 首要维度**不进「匹配项」**：匹配项是已验证达标项，用户最在意的维度未必达标
  （库里可能没有这个维度的数据），硬塞就是编造（见上）。
