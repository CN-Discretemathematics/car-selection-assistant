# 拒绝反馈的影子评估（2026-10-21）

> 分支：`feat/reject-recommendation`（第二笔）｜基线：`origin/main`（第一笔 308c37a 同源）

计划 §四「第五步：Phase 2–4」的第三项：**反馈驱动偏好调整（shadow）**。

第一笔（`308c37a`）做的是「不喜欢这台」→ **会话内**不再推那一台；
它的 docstring 自己写着下一步：「跨会话要靠反馈表 + **影子调参**」。本笔就是那个影子调参。

## 它回答什么问题

把一次「不喜欢这台」**跨会话记住**（计划 Phase 2b 的反馈表）时，粒度有讲究：

- **款型级**（就记住这一台）：安全，但价值有限——下次也就少推一台；
- **品牌级**（上升为「不喜欢这个品牌」）：价值大，但**可能过激**——
  用户讨厌的往往只是那一台的某个配置，不一定是整个品牌。

**品牌级排除的「误伤面」有多大**，是这条产品决策该不该做、该做到什么粒度的证据。
没有这个数就只能拍脑袋——而本仓的纪律是「每个策略决策都要 A/B 实测，不接受未经测量的效果断言」。

## 机制（只算不改）

1. 用户拒绝 → 会话内排除生效（第一笔）。
2. 回答产出后**派发一个旁路任务**（`app/agent/engine.py::_shadow_rejection`）：
   - 查出被拒车所在**品牌**；
   - 构造反事实画像（`brand_exclude_ids` 加上该品牌）→ **重跑一遍推荐**；
   - 算差集：**进了榜 / 掉出榜 / 误伤面**（榜上同品牌的其它车数，被拒那台不算）；
   - 写一条结构化日志（logger `app.agent.rejection.shadow`）。
3. **旁路派发抽成通用的一条**（`_spawn_shadow`）：路由对拍与拒绝影子共用同一份
   in-flight 上限与异常回收——上限、回收、异常归属三处各写一遍必然漂移
   （旁路出错的痕迹会散到不同日志流里，事后查不到）。

口径与算术在 `app/agent/rejection_shadow.py::brand_exclusion_delta`（纯计算，可单测）。

**默认关**（`AGENT_REJECTION_SHADOW_ENABLED`）：影子每次要多跑一遍推荐查询
（全库扫描级开销），不该默认付。开着也**一个字都不改**用户看到的回答。

## 实测（本机真跑：本地快照库 908 车系 + 真实推荐链路）

15 组通用条件组合（预算 12/18/22/28/35 万 × 通勤·家用·长途 × 2~5 口人），
每组两轮：先出推荐，再说「不喜欢这台」。

| 指标 | 数值 |
| --- | --- |
| 触发拒绝 | 15 / 15 |
| 落影子记录 | 15 / 15 |
| **误伤面**（榜上同品牌的其它车数） | 均值 **1.27** · 中位 1 · 最大 3；分布 0:2 · 1:10 · 3:3 |
| 品牌级排除后 top-N 变化率 | **86.7%**（13/15；两次不变的都是「该品牌榜上只有被拒那台」） |
| 掉出榜 / 新进榜 | 各约 1.27 台（均值） |

### 结论（对 Phase 2b 的粒度决策）

**品牌级排除在推荐结果上并不过激**：每次平均只多误伤 **1.3 台**，补进 1.3 台，
榜不会被清空、同品牌的车也不会被一锅端 ⇒ **品牌级是一个可行粒度**，
不是「一拒绝就废掉半个品牌」。
真正该防的是另一种情况——用户只讨厌某一款的某个配置——那时该停在款型级。

⚠️ **这条结论的边界**：它量的是**机制对推荐结果的影响**（可计算、可复现），
**不是**用户偏好本身。计划 §七 仍把「硬约束排除项是记忆的第一价值」标为
**产品直觉、未做用户测试**——本笔不改变那个状态。

## 行为变更

| 场景 | 变更 |
| --- | --- |
| 默认（未开开关） | **无任何变化**（影子不派发） |
| 开启开关 + 用户拒绝 | 用户看到的回答**逐字不变**；后台多一次推荐查询 + 一条结构化日志 |

打分与排序**未变**（反事实只存在于影子内部，不回写画像）。

## 已知边界

- **只覆盖推荐路径**：拒绝只在推荐链路被识别；对比 / 车系问答路径没有「刚推荐的款型」。
- 影子每次要多跑一遍推荐查询——生产开启前要评估并发下的查询量。
- 实测样本是**合成条件组合**（不是真实用户行为）；它量的是机制影响，不是用户偏好。
- 跨会话记忆本身（Phase 2b 的反馈表）**不在本笔**——迁移必须接在分支 8 的迁移之后。
