# 多轮场景评测：跨会话接线、恒真守卫与合流顺序（2026-10-21）

> 配套代码：`backend/tools/eval_multiturn.py`（框架）、`backend/tools/gen_multiturn_scenarios.py`（生成器）
> 分支：`feat/multiturn-eval`
> 本轮实测环境：本地快照库（908 车系）+ 合流 worktree（分支 7 + 17 + 8）

## 一、这份题库要验什么

单轮评测测的是「这一轮答得对不对」，而**个性化功能的正确性几乎全在跨轮之间**：

- 拒过的那台，下一轮还推不推？
- 上次说过的预算，这一轮还在用吗？
- 删掉的记忆，这一轮是不是真的没了？

题库三类场景各 50 道：

| 场景 | 会话 | 依赖 |
|---|---|---|
| `reject_then_no_recommend` | 同会话 | 拒绝功能（`feat/reject-recommendation`） |
| `returning_user_memory` | **跨会话** | 跨会话记忆（`feat/durable-preference-memory`） |
| `memory_deleted` | **跨会话** | 跨会话记忆 + 记忆删除入口 |

## 二、本轮修的五个「假通过」

每一条都是**跑出来的**，不是读代码推理出来的。

### 2.1 框架全程共用一个会话 ⇒ 跨会话场景测的不是跨会话

此前 `run_scenario` 建一个 `session_id` 跑完整场。题库写了「first/second」两个会话标签，
框架**无视标签** ⇒ 所谓「回访用户」其实还是同一个人在同一段对话里。

实测（150 道题）：

| 框架 | 组合 | `returning_user_memory` |
|---|---|---|
| 旧（同会话） | 分支 7 + 17（**没有**分支 8） | **50/50 通过** ✗ 恒真 |
| 新（跨会话） | 分支 7 + 17（**没有**分支 8） | **50/50 失败** ✓ 诚实 |

旧框架里那 50 个「通过」验的是**同会话画像还在**——分支 8 都没合入，
跨会话记忆**根本不存在**。

⇒ 现在每轮按 `session` 标签分配会话：标签变了就换会话，同标签的多轮仍在同一会话；
没标标签的轮次仍共用一个会话（保持旧行为）。跨会话场景还要一个**身份**
（记忆的载体），引擎支持 `handle(identity=...)` 时本场建**一个**、所有会话共用。
引擎不支持时场景判**红**并写明「跨会话记忆无法评测（Phase 1 未接线？）」——
「测不了」不等于「没问题」，悄悄降级会让断言恒真。

### 2.2 「删掉的记忆」场景分不清「删掉了」和「本来就没记住」

旧场景只断言「删完预算不生效」。实测（`DURABLE_PREFS_MODE=off`，记忆功能整体关闭）：

| 场景 | mode=on | mode=off |
|---|---|---|
| `returning_user_memory` | 50/50 通过 | **50/50 失败** ✓ |
| `memory_deleted`（旧） | 50/50 通过 | **50/50 通过** ✗ 恒真 |
| `memory_deleted`（补对照轮后） | 50/50 通过 | **50/50 失败** ✓ |

⇒ 生成器在删除**之前**加一轮跨会话的**阳性对照**（第二个会话断言 `budget_in`——
记忆**还在**），删完再到第三个会话断言 `budget_not_in`（记忆**没了**）。
「还在」与「没了」在同一场内互为对照，不再依赖另一个场景做参照。

### 2.3 拒绝场景的 23/50 是「碰巧通过」

拒绝功能**不在**分支 7 上（它在分支 17）。但在分支 7 上跑，拒绝场景仍有 **23/50 通过**
——那台车只是**掉出了榜单**，不是被拒了。追下去是两层原因：

1. **第三轮候选集被掏空**：第一轮只推得出**一台**车时，拒绝之后没东西可推 ⇒
   第三轮「被拒那台不在榜」是**白送的**（推荐列表为空 ⇒ 那台车当然不在）。
   实测现状句式下第一轮的车系数中位数是 **1**，≥2 个车系的只有 4/20。
2. **场景级守卫管不到它**：「整场无推荐 ⇒ 场景无效」只管整场；
   第一轮推了车、第三轮推不出来时，第三轮的断言照样验不到任何东西。

⇒ 生成器只收**第一轮推得出 ≥2 个车系**的需求（跑真实推荐验证）；
框架新增一条**按轮**守卫：带 `not_recommended` 断言的轮次若**什么都没推荐**，
该轮断言无效（报告里单列 `INVALID(该轮无推荐→断言恒真)`）。

实测：分支 7 单独跑 **23/50 → 1/50**（那 1 个是引擎自己把车排除了，不是拒了）。

### 2.4 第三轮得是「会重推」的问法

第三轮问法与「有没有结构化推荐」（合流分支 17+8 实测）：

| 问法 | 第三轮有推荐 |
|---|---|
| `再推荐几款` | 8/9 ✓ |
| `换个推荐` | 11/11 ✓ |
| `继续推荐` | 8/8 ✓ |
| `还有别的吗` | **0/11** ✗ |
| `再看看其他的` | **0/11** ✗ |

后两种被引擎判成**闲聊**（`is_chatty`）⇒ 走聊天分支、回一句模板、**不重推**
⇒ 第三轮「被拒那台不在榜」是白送的。

追查过「是不是画像被清空了」——**不是**：第三轮画像里 budget / usage / passengers /
body / energy 全在，还带着 `rejected_variant_ids`。是**路由**判成闲聊，
压根没进推荐链路。

⇒ 题库第三轮只收三种会重推的问法（保留多样性，不是只留一种）。

### 2.5 只跑 `enabled` 的场景

题库里 `enabled: false` 的场景依赖**尚未落地**的能力。框架默认跳过它们
（单独报数、**不计入分母**），要强行跑用 `--include-disabled`。

理由：否则「通过率」被未落地的能力拉低，看报告的人会误判成「功能坏了」，
更糟的是有人会去**改断言**让它变绿——这正是本仓反复记录的「不可能变红」陷阱。

生成器侧对应一个开关：

```powershell
python tools/gen_multiturn_scenarios.py --out eval/multiturn.json --enable-memory-scenarios
```

默认关。打开的前提是：**分支 8 已合入**（引擎 `handle` 支持 `identity`）
且 `DURABLE_PREFS_MODE=on`（`off`/`shadow` 模式**不回填**记忆，断言必然红）。

## 三、最终实测（A/B）

同一份题库（150 道），三种组合：

| 组合 | `reject` | `returning_user_memory` | `memory_deleted` | 合计 |
|---|---|---|---|---|
| 分支 7 + 17 + 8，`mode=on` | 49 PASS + 1 INVALID | 50 PASS | 50 PASS | **149/150** |
| 分支 7 + 17 + 8，`mode=off` | 49 PASS + 1 INVALID | **50 FAIL** | **50 FAIL** | 49/150 |
| 分支 7 单独（无拒绝、无记忆） | **1 PASS** + 13 FAIL + 36 INVALID | 50 FAIL | 50 FAIL | 1/150 |

三条读法：

- **记忆场景**：`mode=off` 必红 ⇒ 验的是真跨会话记忆，不是同会话画像（对照轮生效）。
- **拒绝场景**：功能缺失的分支上只剩 1/50 碰巧通过（改之前是 23/50）。
- 那 1 个 INVALID 是**如实报告**：那一轮引擎确实没东西可推（被拒后候选集空），
  框架拒绝把它算成通过。

## 四、合流顺序与冲突（实测）

分支 17（拒绝）与分支 8（跨会话记忆）**都改了 `backend/app/agent/engine.py` 的 `respond()`**，
直接合会冲突。已实测解决，三处：

1. **import 块**：两个分支各加一组 import ⇒ **都留**。
2. **`respond()` 的「0.5) 车系识别与锁定」块**：
   分支 8 把车系/品牌的**解析**提到了函数开头（记忆回填之前，为了让品牌排除项
   能用「本轮的品牌要求」消解冲突），分支 17 在原处加 `_apply_rejection`。
   ⇒ 合流后：解析仍在开头，**拒绝那一步留在原处**（`resolved` 在同一函数作用域内，仍可用）。
3. **`backend/tests/conftest.py`**：两个分支各往「清环境变量」列表里加一项
   （`AGENT_REJECTION_SHADOW_ENABLED` / `DURABLE_PREFS_MODE`）⇒ **都留**。

⇒ **合并顺序建议**：先合分支 17，再合分支 8；分支 7 的评测要等这两条落地才有意义。
分支 7 自身与 17、8 **无代码冲突**（只碰 `backend/tools/`、`backend/tests/`、`README.md`）。

## 五、恒真守卫清单

框架自带三层：

1. **整场无推荐** ⇒ 场景判**无效**（不算通过）——`not_recommended` 是恒真的。
2. **被断言的车从未被推荐过** ⇒ 场景判**无效**——「它不该再被推荐」没验到任何东西。
3. **该轮什么都没推荐**（带 `not_recommended` 断言的轮次）⇒ 该轮断言无效。
4. **未启用的场景不计入分母** ⇒ 防止「未落地的能力」拉低通过率、被误读成「功能坏了」。

题库级（在本轮补上）：

5. **删记忆场景带阳性对照** ⇒ 记忆功能一关，对照轮必红。
6. **拒绝当轮就断言 + 第一轮 ≥2 个候选 + 第三轮是会重推的问法**
   ⇒ 拒绝功能一缺，被拒的车不会「碰巧」掉出榜单就算通过。

每条守卫都有**变异测试**兜底（`.tools/mutate_sess.py`，本地专属不入库）：
7/7 变异全部被用例盖住（去掉换会话、不传身份、不建身份、悄悄放过、
吞掉创建失败、未启用场景照跑、不查该轮空列表）。

## 六、怎么跑

```powershell
# 生成题库（默认只启用同会话的拒绝场景）
python tools/gen_multiturn_scenarios.py --out eval/multiturn.json

# 跑评测（DATABASE_URL 指向当前库）
python tools/eval_multiturn.py --scenarios eval/multiturn.json --report eval/multiturn-report.json

# 只跑某一类
python tools/eval_multiturn.py --scenarios eval/multiturn.json --scenario reject_then_no_recommend

# 连未启用的场景一起跑（看它到底为什么红）
python tools/eval_multiturn.py --scenarios eval/multiturn.json --include-disabled
```

## 七、待立项（本轮发现，不在分支 7 范围）

**「还有别的吗」不重推** —— 用户明确要更多车，引擎却判成闲聊，回一句
「可以告诉我你的预算、主要用途和乘坐人数吗？」（实测 0/11 重推，
而画像里 budget/usage 全在）。这是产品缺陷候选，需要单独分支处理
（涉及路由判定 → 行为变更，需拍板）。

## 八、判据纪律回顾

- 断言只用**结构化字段**：车系类看 `recommended_variants`（散文里提到但没推荐的车不算），
  预算类看 `response.filters` 的区间（正文里的预算必然与车价混在一起，裸字符串双向误判）。
- 锚点用**车系名**，不用 id（单轮题库 410 道里 406 道的 id 锚点指向别的车）。
- 需求句**按构造可满足**：从库里抽真实车系派生品牌/车身/能源/用途/价位，
  并**逐个候选跑真实推荐**验证在榜。
- **价位档两侧各放宽 2 万**（2026-10-21 修正）：原 1 万窄档把候选池压到**中位数 3**
  ⇒「再推荐几款」之后候选集已空 ⇒ 第三轮**推不出任何车** ⇒ 断言无对象可验
  （实测：引擎加上「排除已展示过的车系」后，拒绝场景 49 → 4）。
  放宽后池子**中位数 13**，84% 的需求留得下下一批 ✓。
  窄到个位数验不了「被拒的不再推」，宽到几十台验不了「被拒的那台在榜里」——
  这个宽度是两头都要的平衡点。
- 生成器还要照搬**三轮**（需求 → 拒绝 → 追问）验证「追问后还有新的一批」：
  拒绝轮也会展示一批车，而「已展示过的车系」是**累积**的 ⇒ 两轮累计的排除量更大
  （实测：只按两轮校验时第三轮仍有 15/50 推不出车；按三轮校验后 48/50）。
  该校验**探测引擎能力**：没有「排除已展示」能力时跳过（否则会把所有候选判掉）。
- **一个场景只验一件事**：拒绝理由不夹带会改约束的词（实测 8 个理由的
  「第三轮那台车回来率」完全一样：13/20 ⇒ 理由不是变量，候选集空才是）；
  第三轮不用不会触发重推的问法。
- 零 judge：不用大模型打分，全是二元、确定性的事实判定。

## 九、「50 题/场景足以判定？」——审计给出的答案（含一处更正）

计划 §七把这条列为「未验证的判断」。用分支 24 的审计工具在**全功能分支**生成的题库上实测：

| 变量 | 分布 |
|---|---|
| energy | 纯电 15 / 燃油 32 / 插混 3（**增程 0**、油混 0） |
| price_bucket | 8 种（0-5万 9 / 5-10万 15 / 10-15万 14 / … 35-40万 2） |
| brand | 15 种 |
| body | 轿车 24 / SUV 23 / MPV 3 |
| 拒绝理由 | 价格 16 / 空间 11 / 品牌 9 / 尺寸 7 / 能耗 4 / 外观 3 |
| 分层（价位段×理由） | 25 格，**最小格 1 题** |

**答案**：在「拒过的那台不再被推」这个判据上**够**（每题都在验真实行为 ✓）；
但**按能源/价位做分层比较时不够**（那些格子里只有 1-3 题 ⇒ 统计意义≈1-3 ✗）。

**为什么增程/油混是 0**（这是**产品现实**，不是抽样没做好）：
题库要求「拒过之后**还有下一批**可推」⇒ 该品牌在该价位档必须有足够多的车。
而品牌是**硬约束**（「只要X的」）⇒ 冷门品牌与小众能源的同款车本来就不够两轮
⇒ 它们过不了「三轮校验」，被筛掉 ⇒ 覆盖被**产品现实**卡住，
任何抽样方案都救不回来。

⚠️ **一处更正**：生成器改成分层抽样（能源 × 价位桶两层轮转）后，
在**没有**「排除已展示」能力的分支上，能源确实从「燃油 41 / 增程 0」变成
五种各 7-13、品牌 16 → 20 ✓；但在**全功能分支**上（校验生效 ⇒ 筛掉池子小的车系），
分布几乎回到原样 ⇒ **分层只在幸存候选之间起作用**，它改善的是
「幸存者之间按能源/价位轮转」，不是「把不存在的覆盖变出来」。

⇒ 题库要在**全功能分支**上生成 ✓（否则三轮校验被跳过 ⇒ 第三轮大面积无车可推：
实测 43/50 判 INVALID ✗）。
