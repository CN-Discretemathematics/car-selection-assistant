# 一次性合并，不是实时同步

**状态**：accepted（2026-10-21 用户拍板；实施待立项，方案见
[待立项项落地方案](../2026-10-21-deferred-items-execution-plan.md) 第五节）

## 问题

「登录后，匿名浏览积累的偏好记忆与拒绝反馈怎么办」有两种做法：

- **一次性搬家**：登录时把当前匿名身份的数据搬进账户，搬完匿名身份失效；
- **实时同步**：账户登录期间，每次读写个性化数据都同时读写「当前活跃的匿名身份」。

两者在**功能上**都能让「登录后不再失忆」，但工程代价与失效面完全不同。

## 考虑过的选项

1. **实时同步**：**不采纳**，三条理由：
   - 它需要一个「**当前活跃匿名身份**」的概念——一个账户可以对应多个匿名设备（多浏览器 / 多设备），
     实时同步要么锁死一个（其余设备的数据永远进不来），要么每次读写都扫全部身份
     （每次读一次库、每条记录都要判归属）。
   - 它与 [ADR-0006](0006-anonymous-identity-invalidated-on-merge.md) **直接冲突**：
     旧身份已失效、新的又自动同步 ⇒ 等于绕过「合并后数据不分叉」那道防线。
   - 读写路径上多一次归属判定 ⇒ **同一件事写两遍必然漂移**（本仓反复记录的教训）。
2. **一次性搬家 + 用户再次主动合并**（**采纳**）：每个匿名身份**至多合并一次**，
   合并完即失效；换设备后产生的新匿名身份是**新的独立个体**，用户想搬就再点一次。
3. **不合并**：**不采纳**——匿名浏览积累的记忆在登录后全部失联，
   与「跨会话、可持续个性化」的定位冲突（ADR-0001）。

## 决定

1. 合并是**一次性搬家**，**不是**实时同步。
2. 账户登录期间**新产生**的匿名数据（换设备后重新匿名浏览）**不会**自动进账户。
3. 重复合并同一匿名身份**幂等**：第二次不搬数据；且旧 token 已失效，
   接口返回「不存在、已失效或已合并过」（`auth/router.py:207-209`）。
4. 同键冲突取**较新**的一条（记忆 `identity_merge.py:106`、反馈 `identity_merge.py:133`）——
   记忆是「当前状态」，不是流水账。

## 后果

1. 用户要拿到「**所有设备**的数据」必须**逐设备合并**。
   产品文案必须写「合并**本设备**的数据」，**不能**写「合并所有数据」——
   后者是事实性错误的承诺。
2. 客户端应把**尚未合并**的匿名身份记在本地（token 还在手上 = 还能合并），
   合并成功后清掉；否则用户永远不知道自己还有一份匿名数据没搬。
3. 「同键取较新」这个冲突语义**只对一次性搬家成立**：
   若将来改成实时同步，冲突语义必须重新定义（那时是「最后一次写入赢」还是「按时间线回放」），
   不能直接沿用。
4. 本 ADR 与 ADR-0006 是**一条决定的两面**：一次性 ⇒ 必须失效（否则分叉）；
   失效 ⇒ 必须逐设备重新合并（否则数据搬不进来）。任何一条被单独推翻，另一条都要重判。
