# 不做 agentic RAG

**状态**：accepted（2026-10-20 复核确认）

不使用 agentic 检索（让 LLM 决定检索什么、检索几轮、自改查询），也不用 HyDE 这类「先让 LLM 生成假设答案再检索」的变体。
LangGraph **仅用于**摄取与查询两条检索流水线，**对话主链不用 LangGraph 编排**。

## 理由（有实测数据，不是偏好）

1. **HyDE 已实测有害**：154 题扩样 A/B（`backend/eval/TODO-internal.md` §3）——
   Hit@5 **−1.3pt**、MRR **−1pt**、耗时 **+4.4×**（每题多一次 LLM 调用）。默认关闭。
   另有 451 题消融结论一致，扩样后再次确认。
2. **程序式路由已优于 LLM 路由**：71 条生产输入 A/B，正则路由 **97.2%** vs LLM 路由 **95.8%**。
   对话主链已有 91 条金标、三模式闸门与逐轮留档，换成 LLM 编排是净损失。
3. **与确定性内核冲突**：本仓的卖点是硬约束下推 SQL、答案契约、拒答诚实性。
   agentic 检索的本质是让 LLM 介入「查什么」——这与确定性直接冲突。
4. **收益条件尚不成立**：agentic / 重排类检索的收益要在**有足够语料**时才显现，
   而 `source_document` 类切片**恒为 0**（`SourceDocument.content_text` 恒为 NULL）。
   在「库里没这类事实」的情况下评估「检索不够聪明」是误判。

## 考虑过的选项

- **用 LangGraph 编排对话主链**：不采纳，理由见上第 2 点。LangGraph 已在 RAG 两条流水线使用——那处合适。
- **开 `RETRIEVAL_HYDE`**：不采纳，理由见上第 1 点。

## 后果

- 后续若有人提议 agentic 检索，先问：**是哪条实测数据支持？** 没有数据支撑的提议按偏好处理，默认不做。
- 「重排 / agentic 检索的评测」被排在**文档正文落库之后**——`sparse` 与 `sparse-nooverlap`
  开始出现差异（重叠收益第一次可测）之前，此类评测无意义。
