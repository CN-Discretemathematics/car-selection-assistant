# 车系两级新鲜度与天级发现

**状态**：proposed（2026-10-20 用户拍板，实施随数据管线改造落地）

车系数据分**两级**新鲜度，对外只承诺前者：

- **车系级**（车系名 / 品牌 / 定位 / 价格区间 / 指引价）：**承诺天级**——新车上市当天即可见。
- **款型级**（款型 / 参数配置）：**不承诺时延**——新车上市初期配置表本身可能不全。

发现机制为**天级增量**：`fetch_series_index`（汽车之家 A-Z 车系索引页）每天跑一次，
发现新车系即抓 SKU；同时用库内可信的 `external_id`（1078/1078 映射）定期**探测**，
覆盖「车系还在但款型/参数过期」的情形。

## 理由

1. **发现入口已经存在**。`backend/app/sources/autohome_sku.py` 的 `fetch_series_index`
   （`grade/carhtml/{letter}.html`）**不依赖销量榜**——当前车系发现完全依赖月榜，
   是「新车上市最长 30 天才进库」的根因。
2. **时延收益与成本匹配**。买车决策以天计，「当天就知道」已远超用户预期；
   而实现是**改现有 cron**、做**增量抓取**（只有新增/过期的才抓），请求量几乎不增加，
   与仓库「礼貌限频 ≥1 秒/请求、诚实 UA、遵守 robots」的合规约束不冲突。
3. **不承诺款型级实时**。款型与配置表是几十上百个字段的结构化数据，
   且**新车上市初期配置表本身可能还不全**——承诺「参数当天全齐」是给自己挖坑。
4. **A-Z 索引不能作唯一发现源**。实测记录在 `fetch_autohome_sku.py` 的注释里：
   「凯美瑞」（seriesid=110）不在 A-Z 索引中，但 `fetch_sku_config('110')` 正常返回 13 款型；
   当时的后果是 171 个车系静默无款型。故必须配合月榜与库内 `external_id` 探测。

## 考虑过的选项

- **小时级（每 6 小时）**：索引页请求量翻 4 倍，收益对买车决策无实质差别。**不采纳**。
- **准实时（监听新品发布页）**：延迟可到分钟级，但需新写一个抓取源，
  而汽车之家改版频繁（榜单 SSR 只给 20 行、`__NEXT_DATA__` 结构变更是本仓反复踩的坑）——
  为一个用不上的实时性去赌一个不稳定接口，与仓库纪律不合。**不采纳**。
- **只靠月榜发现（现状）**：最长 30 天延迟，与「可追问」承诺冲突——追问到的是过期答案。**不采纳**。

## 后果

1. **「答不出」必须分三种**，措辞不同：
   | 情况 | 措辞 |
   | --- | --- |
   | 库里有该款型但该参数无值 | 官方资料未披露 |
   | 车系在库但款型尚未抓到 | **该车系配置数据抓取中** |
   | 库里有款型、参数齐全 | 正常回答 |
   混用会破坏可追问性——「官方资料未披露」是**关于事实的断言**，说错一次，信任掉一截。
2. **需要数据支撑，不只是文案**。车系需要 freshness 状态（如 `variants_fetched_at` + `sku_status`），
   让推荐链路与回答链路都能感知缺口。
3. **真缺口与停售必须分开计数**。`export_series_gaps.py` 已有正确的 `NO_VARIANT_WHERE` 判据，
   但既有指标沿用了混合口径，会让回补永不收敛。
4. **覆盖率要常驻可见**。与 `/admin/rag/status` 已有的「车系 908→1078 规模漂移」告警同构，
   车系总数 / 有款型 / 无款型 / 缺口待回补 应进 `/ops` 看板。
