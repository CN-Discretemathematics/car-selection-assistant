# 记忆的边际价值：合成会话上的 on/off 对照（2026-10-21）

> 工具：`backend/tools/eval_memory_value.py`｜题库：`backend/tools/gen_multiturn_scenarios.py`
> 数据源：本地合成会话（`backend/.tmp/eval-local.db` 快照 + 200 题多轮题库）

## 一、它回答哪条判断

计划 §七的第一条未验证判断：

> 「硬约束排除项是记忆的第一价值」——产品直觉，未做用户测试。

这条判断**至今没有任何数据**。本文件给它加一层**机制层**证据：
同一批跨会话场景，**记忆开**（`DURABLE_PREFS_MODE=on`）与**记忆关**（`off`）各跑一遍，
比较通过率（= 1 − 违规率）的差。

## 二、方法

| 项 | 做法 |
| --- | --- |
| 场景 | 多轮题库里的**四类跨会话记忆**场景：预算回访 / 预算删除 / 拒绝跨会话 / **排除项跨会话**（共 223 题 × 2 组 = 446 次运行） |
| 两组 | 同一进程内切换 `DURABLE_PREFS_MODE`（`get_mode()` 每次调用现读环境变量） |
| 隔离 | 每个场景新建一个匿名身份 ⇒ **on 组写下的记忆不会漏进 off 组** |
| 判据 | 每类场景的通过率（on vs off）与差值 Δ |
| 空转防护 | `off` 组若也 100% 通过 ⇒ 该类**不构成对照**（断言恒真），报告里单独标出，不计入「有效」 |

### 「排除项」这一类怎么做到**不恒真**（两条坑，都是实测踩出来的）

1. **断言要落在「品牌」上**：排除项是**品牌级**的（用户说「不要丰田」⇒ 该品牌全部车系出局），
   而库里一个品牌往往有多个车系 ⇒ 逐个车系名比对会漏。
   ⇒ 新增断言类型 `brand_not_recommended`：查**结构化**推荐结果里的 `brand_name`
   （不是正文裸字符串——解释里可能提到「也可以看看 XX」而它**没被推荐**）。
2. **生成时先验一遍「那个品牌本来就在榜」**：否则「它不该再出现」是白送的
   ⇒ 生成器不带排除项跑一次真实推荐，那个品牌的车**确实在榜**才收。
   实测：50 个需求里只有 **23** 个满足（其余 27 个因断言会恒真被丢弃）——
   **宁可少收，不可收成恒真**。

### 第二轮**必须重复硬约束**（否则这类场景又变恒真）

排除项场景的第二轮不能只问「按我之前说的条件推荐」——**没有记忆时**（off 档）引擎手里没有预算
⇒ 它会**反问**「预算大概多少？」⇒ 推荐列表是**空的** ⇒「该品牌不在榜」**白送**
（实测：那样生成的话，off 档 23/23 全过 ⇒ 这类场景证明不了任何事）。

⇒ 第二轮改成「**还是**{同样的硬约束}」：不重复排除项、但重复预算/车身/能源/用途/人数。
off 档于是**也能推出一批车** ⇒「那个品牌在不在榜」才是真判据。

## 三、实测数字（本机真跑）

| 记忆类型 | 场景数 | on 通过 | off 通过 | Δ | 判定 |
| --- | --- | --- | --- | --- | --- |
| **排除项**（品牌级，跨会话还记得） | 23 | **23/23** | **0/23** | +100.00% | 记忆有效 |
| 预算（回访记忆生效） | 50 | **50/50** | **0/50** | +100.00% | 记忆有效 |
| 预算（记忆删除后不生效） | 50 | **50/50** | **0/50** | +100.00% | 记忆有效 |
| 拒绝/排除（跨会话还记得） | 50 | **50/50** | **0/50** | +100.00% | 记忆有效 |

**off 组全红这件事本身就是结论**：它证明这些断言**不是「本来就过」**——
把记忆功能整体关掉，跨会话记忆确实**全部失效**。
（这正是本仓反复记录的恒真陷阱：记忆删除场景曾经「记忆功能关闭时照样 50/50 通过 ⇒
验不到任何东西」，后来补了阳性对照轮才作数。）

### 这一类刚补上就测出两个真缺陷（2026-10-21）

「排除项」这一类**之前根本不存在**（题库里没有 ⇒ 那条判断无从测起）。
补上之后，第一次跑就红了：

| 状态 | on | off | 说明 |
| --- | --- | --- | --- |
| 修之前 | **20/23** | **23/23** | ① off 恒真（第二轮没硬约束 ⇒ 引擎反问 ⇒ 空列表 ⇒ 白送）；② on 有 3 条红，**全是「大众」** |
| 修之后 | **23/23** | **0/23** | 两处都解决 |

② 是**真缺陷**：「大众」属于日常词歧义品牌（理想/长安/大众/未来/启辰/东风），
歧义守卫排在**否定判定之前** ⇒「不要大众」被当日常词丢掉 ⇒ **品牌排除项根本没进画像**；
回填时又按**正向约束**解析记忆里的品牌名 ⇒ 同样落空。
⇒ 全程**没有任何报错**，用户说「不要大众」，系统照常推荐大众。
详见 [生产实况复盘](2026-10-21-production-incident-review.md)「发现五」。

## 四、结论（诚实版）

1. **机制上四类记忆都有效**：关掉就全错，开着就全对（Δ = +100%）。
2. **但四类完全等价** ⇒ 这套**二元**指标**无法给记忆类型排序**。
   「排除项是记忆的第一价值」在合成会话上**得不到支持**（也不被推翻）——
   它仍然是一条**未验证的产品判断**，本文件没有把它变成已验证。
3. **它至少从「不可测」变成了「可测」**：补上「排除项跨会话」这一类后，
   那条判断第一次有了 on/off 对照数据（且当场测出两个真缺陷）。
   真实的**排序**仍然需要真实用户——合成会话只能回答「机制上有没有用」。
4. **真实用户验证仍然缺**：本文件是**机制层**证据，不是用户价值证据。
   2026-10-21 实测生产：`agent_turn_logs` **0 行**；近 14 天 nginx **43,660** 条请求里
   agent 端点只有 `GET /api/v1/agent/sessions`，**消息 POST 次数为 0**
   ⇒ 生产至今没有过一次真实对话，「真实用户测试」这个最终判据当前无从谈起。
   （当晚 15:24 部署后 `agent_turn_logs` 首次有了数据——但那是功能校验自己写的。）

## 五、复现

