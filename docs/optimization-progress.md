## 九、本轮沉淀的工程纪律（2026-10-05）

### 1. 推送前 base 必须是最新 origin/main（用户定规）

写进 `AGENTS.md`，并由 **pre-push 门禁 R5** 机械执行（`check_base_freshness()`）：

  落后不一定冲突，但**落后就意味着评审要在冲突 diff 上做**；

另注：10 条空期望样本的响应状态是 ll_rejected（全部字段未通过校验），
即**「空偏好率 10/10 稳定」是靠封闭失效机制兜住的，不是模型主动没抽**。
这不是问题（B2 只要求不劣化、不编造），但记录在此：它的达成路径与
「模型正确判断为无偏好」不是一回事，别在切流汇报时混为一谈。

**B3 仍未解锁**：判据 1 未过，且判据 2/3 需要生产 shadow 数据

## 十五、第三轮生产实测：品牌硬约束 + 否定（2026-10-05）

补测「只要奔驰，预算30万，别推荐电车」——一句话里同时含**品牌硬约束**、
**预算**、**否定排除**三类约束。站上原样输出：

    只要奔驰，预算30万，别推荐电车
      -> 这辆车的主要用途是什么呢？  [上下班通勤][家庭出行][长途自驾][商务接待]

### N4（高）追问不回执**硬约束**，只回执「侧重」

用户一句话给了三个约束，追问里**一个都没提**：

| 用户已给 | 追问里是否回执 |
| --- | --- |
| 只要奔驰（品牌硬约束） | **无** |
| 预算 30 万 | **无** |
| 别推荐电车（否定排除） | **无** |


ext_clarification 的回执前缀是 _priority_phrase(profile)，而它只读
profile.weights ——**权重里只有「侧重维度」，没有品牌/预算/否定**。
所以 #64 的「追问先回执」只覆盖了「我最看重动力」这一类**软偏好**，
硬约束（用户明确说了「只要奔驰」「别要电车」）仍然一个字不回执。

后果很直接：用户刚说完三个要求，界面回一句「用途是什么」，
他会以为**前面那些话没被听见**。这不是文案瑕疵——硬约束是用户下的**指令**，
被静默吞掉比软偏好被吞掉更伤信任。

（同轮的「这辆车」指代错误由 #65 的 P1-1 修掉，本条不重复。）

### 与 #64「追问先回执」的边界

#64 修的是 _priority_phrase（软偏好侧）。本条指出**硬约束侧完全空白**，
两者是不同代码路径，_priority_phrase 修不到。需另做，且要先定口径：
回执写到多细（全量复述 vs 只提最近一条 vs 只提品牌这类硬性排除）。

## 十六、u10 过度抽取的成因诊断（2026-10-05）

上一节只说「93% 卡在这一条」，但没说清它是**系统性过宽**还是**采样噪声**——
两者修法完全不同，且「噪声」可以合理地忽略。实测重复采样（真实 LLMClient，每条 6 次）：

| 样本 | 消息 | 输出 | 频率 |
| --- | --- | --- | --- |
| u10 | 主要看续航，冬天要跑得远 | 续航 | 6/6 |
| u10 | 同上 | **电池与充电** | **6/6 = 100%** |
| u09 | 我比较看重油耗，别太费油 | 油耗/电耗 | 6/6（单一，正确） |
| u08 | 我最看重后排空间 | 空间尺寸 | 6/6（单一，正确） |

**结论：u10 的过度抽取是系统性的，不是噪声。** 6/6 复现，且另外两条样本
每次都只抽一项、干净。多抽这一项**只出现在 u10**，说明它由该句的某个具体措辞触发。

### 触发源

主要看续航，**冬天**要跑得远 —— 模型从「冬天」推出「低温 → 电池/充电顾虑」。
**这个推断本身不算荒唐**，但金标要求的是「用户明确表达的」，
模型做了一步**超出原话**的推理。

### 根因：提示词缺一条约束

soft_prefs._system_prompt() 只给了 pain_points 的**词表**，没有给
「只抽用户明确表达的，不要替他推断」这类**边界约束**。
于是模型默认「相关即可抽取」。

### 为什么不该改金标

把 u10 的金标补成 ['续航', '电池与充电'] 能立刻让判据 1 变成 100%——
但那是**用实测结果改判据**，正是本项目反复被烧的做法（§0.2、§0.3）。
金标代表「用户实际表达了什么」，不能让输出反过来定义它。

**建议**：在提示词里加一条边界约束（只抽用户明说的；相关不等于被提及），
重跑评测确认跨过 95%。这是一处**正确性修复**，不是口径取舍——
但它会改变抽取行为，且 B3 的门槛正是抽取质量，故仍需拍板后再动。

### 改法

`rank_headlines`（`backend/app/catalog/series_index.py`）在选出极值之后，
先尝试把**展示**换成区间，取不到就退回单值。**极值的选择逻辑一行没动**，
只有展示形态变——`best` 的选取、`ref_unit` 的分组、max/min 的比较全部原样。

区间只在能证明「这几个数是同一个量」时才合成，**三道安全阀**：

| 阀 | 挡的是什么 | 实测命中 |
| --- | --- | --- |
| 单位一致 | `1156 Ps` 与 `850 kW` 不可比 | 动力 513 个车系 |
| **fact_key 一致** | `CLTC综合续航` 与 `CLTC纯电续航里程` 都是 km+CLTC，**却是两个量** | 续航 180 个车系 |
| 测试口径一致 | WLTC 与 CLTC 续航不能写进同一区间 | 油耗 162 个车系 |

## 三十五、扫品牌盘点路径：口语简称解析不到，整个品牌问不到（2026-10-05 18:00）

端到端问了一组「某品牌 + 问车型」，发现**同一类问题里一部分品牌能问、一部分不能**：

| 问法 | 改前结果 |
| --- | --- |
| 「奔驰有几款车」 | ✅ 「奔驰在售车型共 56 款」 |
| 「奔驰**现在**有几款在售」 | ❌ 「抱歉，我这边没有奔驰全系在售车型的完整清单」 |
| 「小米有几款车」 | ❌ **全库盘点**（908 个车系），完全不提小米 |
| 「小米的车型有哪些」 | ❌ 「暂时没有可核对的小米在售车型资料」 |
| 「特斯拉有几款」 | ⚠️ 早期一次实测里 LLM **凭记忆列举** Model 3 / Model Y（不是库内清单） |

**根因**：全库 5 个品牌名带「汽车」后缀（零跑汽车 / 小米汽车 / 理想汽车 / 吉利汽车 /
江淮汽车）而 `aliases` **全为空**。用户口语只说「小米」「吉利」「江淮」——
`resolve_brand_mentions` 只匹配 `brands.name` 与 `brands.aliases`，于是**解析不到任何东西**。
零跑/理想看起来「正常」是因为库里另有一条就叫「零跑」「理想」的品牌记录。

**修法**：在 `_load_entries` 里额外登记**去掉通用后缀**的品牌简称
（`_strip_generic_suffix`，复用 `series_index` 里那套 `_GENERIC_BRAND_SUFFIXES`）。
改后「小米有几款车」「小米现在有几款车」「小米的车型有哪些」一律
答「小米汽车在售车型共 3 款」并列出具体车型。

### 顺带修一个既有缺陷：全名同时命中短名品牌

实测 `resolve_brand_mentions("零跑汽车")` 返回 **[1, 2]**——「零跑汽车」消息同时匹配
「零跑汽车」与「零跑」两个 brand_id（同一公司的两条品牌记录）。长名优先此前只体现在
**排序**上，没落到 span 归属。已加「已被更长品牌名占住的 span 直接跳过」。

### 两条防误伤（写测试时才发现它们各自的可达条件）

1. 简称若**恰好等于另一个品牌的全名**（零跑/理想）则不登记——否则双命中。
2. `AMBIGUOUS_BRANDS` 里的日常词（理想/长安/大众/未来）不登记。

第 2 条我第一版**测不到**：`理想` 恰好被第 1 条挡掉了，这道闸根本没被执行到——
**测试全绿但什么都没验到**。补了「只有 `长安汽车`、没有 `长安`」这个可达形态才真正验到。
而它的真实行为比我以为的更严：连「我想买长安」也**不放行**（日常词宁可漏也不误判），
测试断言按实际设计改写。

### 验证

- `pytest` 全量通过；`ruff 130` = 基线；三道门禁 exit 0
- 新增 `test_brand_short_name.py` 7 条
- **变异验证 4/4**：简称登记撤销 / 防误伤 1 撤销 / 防误伤 2 撤销 / span 归属撤销——每个都打红

### 仍未解决（已登记，待你定夺）

「奔驰有几款车」能答、「奔驰现在有几款在售」却说没有——因为 `_CATALOG_COUNT_RE`
要求出现「车系/车型/款型/品牌」字样，而「奔驰有几款车」不含这些词，于是走的是
**LLM 自行决定要不要调品牌工具**（不稳定：有时调有时不调，早期还凭记忆列举过）。
把「品牌 + 几款/多少款」也接进确定性 `brand_lineup` 分支能消掉这个抖动，
但那是**路由行为变更**（更多问题从 LLM 路径转到确定性路径），不擅自改。

### 两处「改了但从没端到端看过」的补验

**1. 单字名在检索侧认不认**（怕解析认得、检索找不到的割裂）：
`register_tokens` 只在 `ingest.build_chunks` 里跑，注册的是 `display_name`（比亚迪汉）
与 `brand.name`（比亚迪），**不含单字「汉」「炮」**。实测稀疏检索：

    「汉」-> 5 条，命中「比亚迪汉。车型定位：中大型车…」「比亚迪 汉 2025款 EV 智驾版 506KM尊贵型…」
    「炮」-> 5 条（「夏」-> 0 条，符合预期：夏 不在允许表）
    「比亚迪夏」-> 5 条

结论：检索侧本来就靠 chunk 文本里的全名命中，**没有引入割裂**。

**2. 版本路径的路由缺口修好后的真实效果**（此前只验过解析层，没看过产品输出）：

    Model Y有哪些版本   -> 【特斯拉Model Y】在售 3 个版本  ✅（修前拿不到）
    Model Y分几个版本   -> 【特斯拉Model Y】在售 3 个版本  ✅
    星愿哪个版本好     -> 【银河星愿】在售 6 个版本      ✅
    星愿哪款值得买     -> 【银河星愿】在售 6 个版本      ✅
    汉各个配置怎么选   -> 走单车系档案（已登记的已知未覆盖）
    星愿有几种配置     -> 走单车系档案（同上）

**再次印证本会话的主线教训**：解析层、渲染层、检索层各自都对，不代表产品输出对。
这一轮 5 个缺陷里有 4 个只有在**整条链路跑完**时才看得见。

## 三十六、扫多轮会话：会话里已锁定的车系在对比时被忽略（2026-10-05 18:20）

本会话所有验证都是**单轮**的。两轮对话才是销售助手的主场景，而**会话状态这一维
从没端到端跑过**。跑下来第一条就出问题：

    第1轮「汉怎么样」    -> 「比亚迪汉」：中大型车 · 轿车 · 插混 / 纯电 · 官方指导价 16.88-22.58 万元
    第2轮「和汉L比呢」  -> 「可以告诉我你的预算、主要用途和乘坐人数吗？」

用户明确要做**对比**，系统反过来问预算——而且把已经在具体车系语境里的用户
拉回了零起点。固定第一轮锁「汉」，只变第二轮问法，10 条实测：

| 第二轮问法 | 本轮解析出 | 结果 |
| --- | --- | --- |
| 「和汉L比呢」/「跟汉L比一下」/「跟汉L比」 | 只有汉L | ❌ 问预算或走其它链路 |
| 「它和汉L差在哪」 | 只有汉L | ❌ 其它 |
| 「汉L能买吗」 | 只有汉L | ❌ 其它 |
| **「对比一下汉L」** | 只有汉L | ❌ **给了单车系档案，根本没对比** |
| 「汉L怎么样」/「汉L续航多少」 | 只有汉L | ✅ 单车系档案（正确） |
| 「汉L和汉哪个好」/「汉和汉L比」 | **两台都在本轮消息里** | ✅ 对比 |

**规律很清楚**：只要两台车里有一台**只存在于会话历史**（而非本轮消息），对比就丢失。

**根因**：`should_answer(resolved, message)` 与后续对比分支只看 `resolve_series(message)`
的结果——即**只解析本轮消息**。会话里锁定的车系（`profile.locked_series_ids`）
在本轮没被点名时不参与，于是 `len(resolved) == 1` → 走单车系档案 / 追问。

**只给触发词加「比」是不够的**：那样 `should_answer` 会为真，但仍只有 1 个车系，
走的是 `_describe` 单车系档案，**依然不是对比**。对症的改法是在路由层：当消息带
对比/指代标记（对比/比较/相比/哪个好/差在哪/跟…比）且会话锁定了**另一台**车系时，
把锁定的那台并入 `resolved`。

**属路由行为变更**（更多问题从追问/推荐链路转到确定性对比路径），不擅自改，已登记待拍板。

### 顺带记一条：单轮里也有同类答非所问

「对比一下汉L」在**单轮**（没锁任何车系）时同样给的是单车系档案。
若消息里的「对比」是泛指（没有第二台车可比），给档案也许可接受；
但用户明说「对比」而系统没做任何对比，至少应该在文案上说明缺哪一台。
本轮**未改**，只登记。

## 三十七、量「追问收敛速度」，并推翻我自己两个疑似缺陷（2026-10-05 18:30）

### 收敛速度：3~4 轮

| 开场 | 拿到推荐用了 |
| --- | --- |
| 「我想买台15万的纯电轿车」 | 3 轮 |
| 「预算20万想要SUV」 | 3 轮 |
| 「推荐一台好开的车」/「给我推荐个车」/「有什么热门的车」 | 4 轮 |

**但追问文案里那句「（主要用途、乘坐人数也一起说一下，**我一次排完**）」是兑现的**：
一次性把三个维度说全，第 2 轮直接给推荐（实测「预算15万，通勤用，两个人坐」→ 当轮给出 2 个车系）。
文案没有说谎，慢是因为用户**没有**一次给全。这条**不是缺陷**，是设计取舍，
记下来是因为它决定了追问文案怎么写才诚实。

### 疑似缺陷一：预算给了还在追问 —— **推翻，我自己的探针错了**

初判：「十万以内有什么推荐」「15万左右买什么」等 8 种带预算的问法**全都在追问预算**。
查实际追问文本后发现**预算收下了**：

    「10万以内有什么推荐」 -> 「已记下：预算不超 10 万。主要用来跑什么？」
    「20万预算推荐几款」   -> 「已记下：预算不超 20 万。主要用来跑什么？」

我的探针把追问文本**截断到 20 字符**再做子串判断，而回执本身就含「预算」二字
（「已记下：预算不超…」），于是必然误判。**不是产品缺陷。**

### 疑似缺陷二：说「热门」却答「没数据」 —— **无法在本快照上验证**

LLM 对「有什么热门的车」「本月销量榜」答「没有可用的销量数据，不能编一个排名」。
但本地快照的月销量只有：

    行数 40，覆盖车系 26 个，月份 ['2026-07', '2026-05']

而代码注释称生产是「2026-09 补齐销量数据后**单月 650 个车系**」。
**本地快照严重不完整，不能据此判定生产缺陷**——若生产真有 650 个车系的月销量，
那这条就是真缺陷（该能答的说没有）；若生产也不全，那 LLM 的拒答反而是诚实的。
**登记为「需生产数据确认」，不下结论。**

### 本会话第四次「探针判据误导」

同一个模式今天出现四次：

1. `n in g or g in n`——拿**子串包含**当等价匹配
2. 「全库渲染 diff = 0」——只替换**标签侧**函数，结构上看不见值侧变化
3. `_split_embedded_unit` 的反例选了「米其林AT」——形状不对，测不出任何东西
4. 追问文本**截断到 20 字符**再做子串判断

**共同根因：用局部的、近似的判据下全局结论。**
每次都是「红/绿」看起来合理，实际验的不是同一件事。

## 四十、④ 的根因定位与修复：守卫让出了车系问答，但 0.75 根本接不住（2026-10-05 19:20）

上一节把 ④ 标为「已实现，未验通」。这一节把根因找到并修掉。

### 复现（真库 + 真 `decide_route`，不是读代码推测）

搭了 3 款合成车系（比亚迪 / 汉 / 汉L），按真实多轮时序喂进去：

```
第1轮「预算20万，汉怎么样」   → 锁定汉，画像 budget=18-28 万
第2轮                        → 并入后 len(resolved)=2
```

| 第2轮消息 | 有预算 | 无预算 |
| --- | --- | --- |
| `对比一下汉L` | **recommendation** ❌ | tool_loop ✅ |
| `汉L和汉哪个好` | series_qa ✅ | series_qa ✅ |
| `和汉L比呢` | series_qa ✅ | series_qa ✅ |
| `汉L跟汉比一下` | series_qa ✅ | series_qa ✅ |

**缺口只影响含「对比」二字的消息**，因为 `_CONTRAST_ASK_RE = re.compile(r"对比")`
——它只认这两个字，「哪个好 / 比呢 / 比一下」全都不匹配守卫。

### 根因：守卫与 0.75 各写一份条件，已经漂移

0.65 守卫的语义是「对比问题让给工具循环」——它**假定** 0.75 一定接得住：

```python
if not (_CONTRAST_ASK_RE.search(message) and len(resolved) >= 2):
    return series_qa            # 让出去
```

但 0.75 还要求 `not profile_core`（画像无预算/人数/用途），守卫**没算这一条**。
于是：守卫让出 → 0.75 被 `profile_core` 拦下 → 一路掉到
`4:recommendation_fallback` → 答「预算大概多少？」

**用户第 1 轮就把预算说过了，第 2 轮反而被再问一次。** 最本质的错不是答得不好，
是**答非所问**：用户已经点名了两台车，事实全在库里。

无预算时之所以正常，正是因为 0.75 的前置条件恰好都满足——守卫的注释描述的那个场景。

### 修法：不补条件，收敛到一处

没有给守卫「补上 `not profile_core`」——那只是把同一个 bug 抄第三遍，下一次
有人改 0.75 的条件它又会漂移。改成**让守卫问一个和 0.75 完全同源的问题**：

- 抽出 `_car_context()` 与 `_tool_loop_eligible()`（0.75 前置条件的唯一实现）；
- 0.65 守卫改为 `... and _tool_loop_eligible(message, hints, profile, resolved, db)`；
- 0.75 本体也改调同一函数。**两边不可能再漂移**——漂移需要复制一份条件。

守卫没接住时留在车系问答，它本来就支持多车系对比
（`build_series_qa_answer` 的 `" vs "` 拼接）。

**没有为了让对比进工具循环而去放宽 0.75 的 `not profile_core`**：那是 2026-09-15
一条带日期的明确决定（「带约束的继续走推荐链」），动它要用户拍板，不在本次范围。

## 四十六、PR #71 推送后的自查：**撤回一个我引入的真回归，并改掉一个我自己写错的解释**

### ① 撤回：把 `~` 加进多值分隔符，**在真实数据上制造了静默降级**

第四十五节之前我按独立审查 P1-3 的建议，把 `~` 加进了 `_MULTI_VALUE_RE`

```
含 `~` 的 fact_value 行数：23
  其中同时含 / 、 ，（本就会被判多值）：0
  只有 `~`、原先不会被拦下的：23
    9x  最大扭矩转速(rpm) = '1500~2400'
```

（变异：把 `~` 加回去 → 变红）。

### ② 候选台数用 `count()` 求和，把「或者」数成两个

候选台数的估算函数原本逐项 `count()` 求和，而连接词表里
同时有 `或` 与 `或者`——`或者` 含 `或`。于是「买A**或者**B」被数成 **3 台**：

```
'买A或者B'      -> 隐含候选 3 台    ← 正常的两车问题会误报「你问的 3 台只查到 2 台」
'A和B或者C和D'   -> 隐含候选 5 台
```

这是**披露逻辑自己的误报**，比漏报更糟——用户会看到一句莫名其妙的免责。
改为 `findall` 整体匹配，并补 `、`（中文枚举首选，真实问句里就有
「目前看了海豹、极氪007、小米su7」）。**不含 `,`**：逗号在正常句子里只是停顿，
计入会让每个逗号句都被当成并列。

### ③ 我自己写错的解释，变异测试打脸

改用 `findall` 时我顺手把注释写成「必须**最长优先**交替，否则 `或者` 会被
`或` 抢先」。变异测试把 `或` 排到 `或者` **前面**——**17 条全绿，没被抓到**。

因为这个理由本身是错的：`re` 交替虽是最左优先，但**计数场景下顺序不影响结果**。
「或者」无论被哪个分支吃掉，**匹配数都是 1**。真正的关键只是「用 `findall`
而不是把 `count()` 相加」。注释已改成如实说明，并留了「别被『最长优先』这个
说法误导」这句提醒——**一条错误的注释比没有注释更坏，它会让下一个人以为规则
里有约束而放松验证**（这与我在 `test_sales_ranking_matches_home_endpoint_caliber`
上犯的是同一类错）。

反向验证：退回 `count()` 求和 → 2 条红（`买A或者B`、`A和B或者C和D`）。

### 顺带发现 `scan_secrets.py` 的一个真缺口（未改，留待拍板）

写这条台账时 `reviewer/scan_secrets.py` 报了一条 MEDIUM 误报，根因清楚：

- `HIGH_ENTROPY` 是「24+ 位 `[A-Za-z0-9+/_-]`」，`_implied_candidate_count`
  正好 **24** 个字符 → 命中；
- 同一行出现 `token` → 命中密钥类关键词；
- 放行规则 `_looks_like_identifier_or_path` 的 snake_case 正则是
  `[a-z][a-z0-9]*(?:_[a-z0-9]+)+`，**要求以小写字母开头**，
  于是带前导下划线的标识符（`_foo_bar_baz`）**不在放行之列** → 上报。

即：**任何以 `_` 开头、长度 ≥24 的 snake_case 标识符，与 token/secret/key 同行必被误报。**
这在 Python 代码注释里很常见（`_private_helper_name`），不是个案。

**没有动门禁**：动 `reviewer/scan_secrets.py` 属改门禁，须 `security`/`gates` scope
+ `# gate-allow:` trailer，且按 AGENTS.md 规则 6 不能顺手把「修自己」和「用自己」
混在一笔里。正确修法是把那条正则改成 `[a-z_][a-z0-9]*(?:_[a-z0-9]+)+`，
另开一笔带自测的提交。
