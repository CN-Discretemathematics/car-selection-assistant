### 1.2 三条口径规则

1. **只评锚定题**：`eval_rag.py` 的 `_run_strategy` 对无法解析出关联车系的题直接跳过
   （`if not rel_series: continue`），因此 520 题主库实际评测 451 题。
2. **报告不入库、CI 不重跑**：题库与报告都在 `.gitignore` 内，CI 只跑确定性测试与静态门禁；
   评测表是「某次运行 + 某份报告」的快照，复现需要题库 + 生产库 + 云端 embedding/rerank。
3. **可移植锚点**：题面锚定的是生成时的数据库行 id，`_portable_anchors` 会按
   「行 id 仍存在且题面出现该车系名 → 保留；否则退化为题面中最长车系名 → 再否则保留原锚点并记 stale」
   重新对齐，报告里带 `remapped / stale / stale_ratio`。**stale_ratio 过高时整份对比作废。**

## 2. 指标含义

### 2.1 检索指标（`eval_rag.py` 的 `_metrics`）

| 指标 | 定义 | 读法 |
|---|---|---|
| Hit@K | top-K 中是否至少命中 1 个相关车系 | 「用户问的车系有没有被召回」，最宽松，适合看兜底能力 |
| Recall@K | 命中的相关切片数 / 该车系的全部索引切片数 | 受切片总量影响，长车系天然偏低；报告同时给 `recall_ceiling`（denominator 上限），**比较时看 recall / ceiling** |
| Precision@K | top-K 中相关切片占比 | 「召回里有多少是噪音」，K=5 时受切片粒度影响 |
| MRR | 第一个相关结果的倒数排名（1/rank） | 「正确答案排多前」，对头部敏感 |
| NDCG@K | 按相关性位置折损的归一化排序质量 | 排序质量的综合指标，适合看「整体顺序对不对」；@5 看头部、@10 看长尾 |

### 2.2 语义约束指标（v2 口径）

v2 针对「推荐/参数/对比」三类问题分别判「回答语义是否满足约束」，不再只看车系是否召回：

| 指标 | 判定队列（451 题集） | 含义 |
|---|---|---|
| fact-coverage@5 | 参数类 47 题 | top-5 切片是否覆盖问题要求的全部参数键 |
| valid-hit@5 | 推荐 + 语义 156 题 | 是否给出「满足硬约束的车型/切片」 |
| valid-precision@5 | 同上 156 题 | top-5 中满足约束的比例 |
| valid-MRR | 同上 156 题 | 满足约束的结果排多前 |
| pair-coverage@5 | 对比类 41 题 | 对比双方是否都在 top-5 中被覆盖 |

注意：v2 的数字对**判定队列大小**敏感。531 题跑法的 valid 队列是 236（主库 156 + 多约束 80），
与 451 题跑法的 156 不是同一个分母，跨表比较前先确认 n。

### 2.3 生成层指标（`eval_judge.py`）

对 100 条分层抽样回答，用独立 judge 模型（`qwen3.8-flash`）按桶各取 25 条打分：

| 指标 | 含义 |
|---|---|
| faithful_rate | 回答与检索证据一致（无编造）的比例 |
| faithful_db_rate | 回答与数据库事实一致的比例（比 faithful 更严格，要求事实级正确） |
| complete_rate | 参数类回答把要求的参数答全的比例 |
| double_judge_agreement | 同一条回答两次独立打分的一致率，衡量 judge 自身的稳定性 |

### 2.4 行为层指标

| 指标 | 含义 |
|---|---|
| 拒答通过率 | 60 道无答案题中「明确说不知道/不编造」的比例 |
| 多约束命中 | 80 道多约束题的硬约束是否满足（hit@5 看车型是否出现，valid-* 看约束是否满足） |
| 口语化劣化 | 同一问题改写后的指标相对原题下降多少，衡量鲁棒性 |
| 解析鲁棒率 | 约束解析器在 490 条变体句式上成功解析的比例 |
| 可追问率 | 回答里每个数字/句子能否追溯到证据（数字级 = 每个数字有来源，句级 = 每个句子有来源） |

### 2.5 工程指标

| 指标 | 含义 | 测量方式 |
|---|---|---|
| 切片数 | 索引规模（随语料增长） | `build_retrieval_index.py --dry-run` / `dense-build-meta.json` |
| load+chunk 耗时 | 从 DB 读全量语料并切片的耗时 | 本地跑 dry-run 计时（含隧道延迟，非生产机 CPU） |
| 全量重建耗时 | dense 索引全量重建（embedding + 写 Zilliz） | 服务端 `rebuild*.log` |
| 端到端延迟 | 单题检索 + 重排 + 生成的墙钟时间 | eval 报告的 `elapsed_seconds` |

## 4. 结果解读

1. **头部稳住、长尾变好**：Hit@5 与 MRR 几乎不动，NDCG@10 +2.6pt，说明优化作用在「排对顺序」而不是
   「多召回几个」；分桶看，提升主要来自推荐桶与语义桶的排序，参数/对比桶已在 1.0 附近没有空间。
2. **v2 约束满足大幅提升，但要先排除分母差异**：§3.3 已统一到 451 题/同队列（47/41/156）；
   旧 README 把 531 题（valid 236）的 0.8136 与 451 题（valid 156）的 0.9872 并排，差值被夸大。
   统一口径后真实提升是 valid-hit +19.9pt、precision +36.5pt、MRR +28.5pt。
3. **数据增长是共同变量**：语料 908 → 1,102 车系、切片 12,078 → 14,032，召回候选变多。
   本次没有做「同一索引回放旧数据」的消融，因此严格归因需要后续补 A/B；文档只陈述「同一口径下的前后值」。
4. **耗时不能跨环境比较**：本次经 SSH 隧道访问 RDS，且重排/embedding 走云端 API，663.6s 与历史 418.9s
   不是同一测量条件；工程表里保留历史直连数字并注明环境，避免读者误读为性能退化。

## 6. 复现方式

```bash
# 1) 题库（只用生产库生成，默认会覆盖 eval/questions.json，务必先备份）
cd backend
python tools/gen_eval_questions.py --output eval/questions.json

# 2) 检索 + 语义约束（稀疏单路，不依赖云端，约 20s）
python tools/eval_rag.py --questions eval/questions.json --only sparse --report eval/report-sparse.json

# 3) 生产配置（稠密走云端 + 重排 + 答案生成，约 10min、约 ¥0.3–1）
python tools/eval_rag.py --questions eval/questions.json --only pipeline --with-dense --report eval/report-pipeline.json

# 4) 生成层（需要 judge 模型 key，约 5min、约 ¥1–2；默认 100 条抽样）
python tools/eval_judge.py --limit 100

# 5) 拒答（需要 LLM key，约 1min）
python tools/eval_agent.py --questions .tmp/questions-unanswerable.json

# 6) 可追问率（确定性模板，不调用 LLM）
python tools/eval_traceability.py
```

约束：

- `.env` 里的 `DATABASE_URL` 指生产 RDS 公网地址；本地复测需自行建只读通道（SSH 隧道或 RDS 白名单），
  不要为了复现把生产库口令写进脚本。
- **不要**执行 `build_retrieval_index.py --target dense` 或 `verify_zilliz.py`：前者会 drop/create 生产
  Zilliz collection，后者会写入假向量。
- 生成层/拒答复测时设 `AGENT_CONVERSATION_LOG_ENABLED=false`，避免写生产会话日志；多轮/记忆类评测会写
  Redis 与数据库，**不在只读复测范围内**。
- 报告一律显式传 `--report <path>`：`eval_rag.py` 默认写 `eval/rag_eval_report.json`，会覆盖历史基线。

## 7. 局限与风险

1. **单次运行**：检索指标是确定性脚本，但 dense/rerank 走云端 API，单次结果有网络与模型版本波动；
   本次与基线各只有 1 次运行，±0.5pt 内的差异不应过度解读。
2. **题目锚点会漂移**：题库锚定生成时的数据库行 id，车系下线/合并会让部分题不可解析（stale）。
   本次复跑锚点重映射后 stale 比例正常，但跨月对比前必须检查报告的 stale 字段。
3. **judge 抽样小**：生成层只抽 100 条（分桶 25），结论适合看趋势，不适合做小数点后比较；
   `double_judge_agreement 0.913` 说明 judge 本身有约 9% 抖动。
4. **无 CI 回归**：评测依赖生产库与云端模型，目前不进 CI；回归靠人工在发版前跑（本文件就是存档）。
   若要自动化，需要先固化「题库 + 只读副本 + 指标阈值」，这是后续工作项。
5. **LLM 抽样与多轮评测未重跑**：真实 LLM 可追问率、多轮/跨会话、记忆价值等套件要么花 LLM 预算、
   要么写生产数据，本次范围只覆盖确定性模板与检索/生成主指标；确定性模板可追问率本次已完成（见 §3.6）。

6. **生成层复测非严格同条件**：judge 本轮报告 errors=0，但复测期间 DeepSeek API 偶发 `ReadError`
   触发工具循环回退，且作答模型/提示与语料规模与基线不同；§3.4 的本次列只作观测，
   不宜当回归结论（详见 §3.4 †）。
