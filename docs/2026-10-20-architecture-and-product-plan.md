## 三、与产品方案的融合

### 3.1 方案的两处需要修正

**修正一：D1.2「31 个停售车系补抓」不是缺口。**

`export_series_gaps.py` 的 docstring 已给出正确判据：

> **真缺口**（完全没有任何款型，回补目标）与「有款型但全部停售」必须区分开——后者数据是完整的、
> 上游就把这些款型标为停售，详情页显示「暂无在售款型数据」本就正确。

方案自己也困惑了（Unresolved Decisions 1：「`active_status` 与『全部款型停售』标记如何并存？」）。
**正确做法**：真缺口 = 完全无款型（201 个在售车系有销量但 0 款型）；停售不进缺口指标。
用 `NO_VARIANT_WHERE` 这个已存在的正确判据，别用混合口径。

**修正二：Phase 0 的排序理由要补一条依赖。**

方案说 Phase 0 排最前是因为「不引入模型不确定性 + 顺带产出多轮评测与文档正文所需的真实数据」。
补一条：**车系天级发现是「可追问」承诺的硬前提**——数据不实时，可追问就是追问到一份过期答案（ADR-0004）。

### 3.2 方案的顺序需要一处提前

方案的依赖链是「Phase 0 产数据 → Phase 5 建多轮评测 → Phase 1–4 靠多轮评测验收」，
**但 Phase 5 排在最后**——Phase 1–4 的验收判据在最后才具备。

**修正**：把「多轮评测**框架**」从 Phase 5 提前到 Phase 0 之后（只提前框架，不提前数据），
空的题库（20–30 题，场景定义齐全、可用 mock 数据）先立起来。
否则 Phase 1 做完了只能靠「感觉记忆生效了」判断——**这违反方案自己 D0 定的纪律**
（「每个策略决策都要 A/B 实测，不接受未经测量的效果断言」）。

### 3.3 多轮题库规模

| 场景 | 题量 | 判据 |
| --- | --- | --- |
| 拒绝后不再推 | 50 | 二元可判（推了/没推某台），不需要 judge |
| 回访用户记忆生效 | 50 | 覆盖预算 / 用途 / 排除项三类 |
| 记忆删除后不再生效 | 50 | 二元可判 |

**参照系**：现有单轮语料 520 题（recommend 246 / parameter 115 / semantic 80 / compare 79）、
金标路由 91 条、拒答 60 条。50/场景不算虚高。

**但**：多轮题比单轮题难造——「车辆 + 拒绝原因 + 后续问句」的组合里，**拒绝原因在库里不存在**
（反馈表是 Phase 2 才建的）。所以第一版只能「模板 × 真实库抽样」混合生成：
从生产库抽 N 台真实车（覆盖不同品牌 / 价位 / 车身 / 能源），对每台机器生成 2–3 种拒绝原因与后续问句组合。
**必须保证每场景 50 题在关键变量上有分布**（品牌数、价位段、拒绝维度各覆盖多少），
否则 50 题的统计意义≈5 题。

判定口径复用既有机制（沿用 `gen_eval_questions.py` 的分层抽样与校验重构），
不新建一套判定标准。

## 五、新增的可度量指标

### 5.1 可追问率

**定义**：随机抽 N 条已回答的问题，把答案给用户看并问「这句话的依据是什么」，
系统能自动给出该句数字出处的比例。

**为什么必须加**：目前评测量的是「检索准不准」「答得对不对」，
**没有量「用户能否问出这句话的出处」**——而这是唯一的差异化承诺（ADR-0003）。
没有度量，差异化只是口号。

**实现成本**：`answer_contract.py` 已有 `allowed_numbers` / `allowed_names` 与 `source_id` 的现成结构。

### 5.2 覆盖率看板

车系总数 / 有款型 / 无款型 / 缺口待回补（真缺口与停售分开计数），
与 `/admin/rag/status` 已有的「车系 908→1078 规模漂移」告警同构。
